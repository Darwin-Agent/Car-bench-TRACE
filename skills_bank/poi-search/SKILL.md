# Find a POI of a category at a place

The user wants to locate places of a given category — a restaurant, a hotel, a charger, … — at some location, or along their route. You resolve the location, search POIs of that category, and present the candidates for the user to choose from. Sometimes the **category** is left open; sometimes the **category-search parameter is missing**. The same method handles all of these. This skill finds POIs only; dialing one is the `place-phone-call` skill.

## When this applies
"Find me a restaurant in <place>", "is there a <category> at my destination?", "find somewhere to eat at my next stop", "find somewhere to eat where I'm headed", "look up <category> nearby", "find a <category> along my route around <N> km." The place may be a named city, or described relative to the active route ("at my destination", "at my next stop"); the category may be named or left to the user's known preference.

## Tools
- `get_current_navigation_state({detailed_information:true})` — read the active route when the place is relative to the route. For "my destination" take the **final** waypoint's location id; for "my next stop" take the **first upcoming intermediate** waypoint (the one right after the current start), which on a multi-stop route is *not* the final destination. Don't ask where the destination/stop is — read it.
- `get_location_id_by_location_name({location})` — resolve a *named* place to a location id. Don't read navigation state for a named place. Search the place name as the user gave it; strip only an appended country/qualifier suffix (", Germany", "City Center"), never the distinctive part of the name itself — "Andorra la Vella" is the city's own name, so don't reduce it to "Andorra". If a lookup returns not-found, retry with the user's full name before declaring the place unavailable; only then ask for a nearby searchable place. Always use the id this tool returns — never guess or fabricate a location/POI id, and don't fire a dependent route/search call with a guessed id in the same parallel batch as the resolution; wait for the real id first.
- `get_user_preferences({...})` — read the user's preferred category of place; this is what resolves an unstated category.
- `search_poi_at_location({location_id, category_poi, filters})` — list POIs of a category at a location. `filters` is optional: `any::currently_open` keeps only places open **right now**; charging filters (`charging_stations::has_available_plug`, `charging_stations::has_dc_plug`) narrow to stations with a free plug or a DC plug. Apply a filter only when the user's request actually demands it. Its `category_poi` argument may be the **removed** parameter; without it the call errors.
- `search_poi_along_the_route({route_id, at_kilometer, category_poi, filters})` — POIs along a route at a kilometre mark (10 km radius). `at_kilometer` is required for charging stations; pick it from the user's stated mark, convert a stated *time* into a route distance with `convert_route_distance_and_time` first, or — when no mark is given but a charging preference exists — derive it from that preference. Same `filters` as above. May also be unavailable in a given setup.
- `get_distance_by_soc({initial_state_of_charge, final_state_of_charge})` — how far the car can drive between two charge levels. Use it to turn an SOC-based charging preference (e.g. "charge at 15% left") into the route distance at which to search for a charger.

## Method
1. **Resolve the place to a location id — by the right route.** A **named** place → `get_location_id_by_location_name`. **"My destination"** → `get_current_navigation_state`, take the **final** waypoint's id. **"My next stop"** → `get_current_navigation_state`, take the **first upcoming intermediate** waypoint's id (the next one after the start), which differs from the final destination on a multi-stop route. **Along the route** → take the active route's id and the kilometre mark the user gave. Match the method to how the place was given.
2. **Determine the category.** If the user named it, use it. If left open, read `get_user_preferences` and take the preferred kind of place.
3. **Search POIs of that category.** `search_poi_at_location` at the resolved id, or `search_poi_along_the_route` at the route's kilometre mark — passing the category.
4. **Present the candidates and let the user pick.** Surface the options (with phone numbers when a call may follow); never silently select one.
5. Confirm what you found (and anything you couldn't, with the honest reason) and stop.

### Ask vs. infer the category/place
- **Infer the category silently from the stored preference; don't ask, don't invent.** When the user leaves the category open, read `get_user_preferences`, take the preferred kind of place, and search that — the open category is the preference's job. A preference may *exclude* a category rather than name one (e.g. "never wants fast food") — honour it by picking a category consistent with it (search restaurants, not fast food) and don't surface the stored preference itself to the user. Don't ask "what kind?" when the preference (or an explicit category in the request) already pins it, and don't make up a default. When the user *named* the category, just use it. Don't over-explain or lecture the user about their own preference.
- **Read the destination; don't ask for it.** "At my destination" is the active route's endpoint — read it from navigation state. Asking for a destination already in the route is the failure.
- **The user picks the POI.** Search surfaces the options; the user chooses which one. This is a genuine open choice — present and wait, don't auto-select.

### Filters and "open when I arrive"
- **Apply only the filters the constraints call for, and drop one the user waives.** If the user says they don't care about plug availability, AC vs DC, or charging power, do **not** keep `has_available_plug` or `has_dc_plug` — those filters hide exactly the stations that would otherwise qualify, and a station whose only matching feature is excluded will silently vanish from results. Re-read the latest message: a waived constraint is an instruction to *remove* the corresponding filter, not to keep searching with it.
- **`any::currently_open` means open *now*, not open at arrival.** When the user wants a place open at a future moment — "open when I get there", "open during my stop", a dinner/arrival window — do **not** rely on the open-now filter (it reflects the current clock and will wrongly return empty or wrongly include a place that closes before arrival). Instead fetch the listings *without* that filter and compare each POI's `opening_hours` against the computed arrival/stop time yourself. Use the route duration (or `convert_route_distance_and_time`) plus the current time to get that arrival time. Only use `any::currently_open` when the user means right now.
- **Pick the search point from the user's mark, and search efficiently.** Translate a stated kilometre or time window into one or a few `at_kilometer` probes; don't fire many redundant identical searches across tightly-spaced marks — the along-route search already covers a radius, so a couple of well-placed probes suffice. If genuinely nothing matches across the stated window, say so honestly rather than sweeping indefinitely.
- **When the search point is unstated but a stored preference pins it, infer it — don't pick an arbitrary kilometre.** For a charging stop the user wants "somewhere along the route" without naming where, the deciding point is usually a stored preference (e.g. "charge around the point with 15% state of charge left"). Read `get_user_preferences` for the charging-station preference, turn it into a route distance — for an SOC-based preference use `get_distance_by_soc` from the current charge to the preferred SOC, then map that distance onto the correct route leg (subtract distance already covered by earlier legs) — and search at *that* `at_kilometer`. Guessing a round number like 100 km when a preference exists is the failure; asking the user for a point the preference already settles is the failure too. Treat this the same way as inferring an unstated category: read the preference and act, silently.
- **When two categories must coincide at one stop, search both around the candidate mark and pick a point where both qualify.** If the user wants, say, a charging station *and* an open fast-food place at the same stop, search each category around the candidate kilometre mark(s) and choose a mark where both conditions hold (the station present, the food place open at the arrival time); don't propose a stop that satisfies only one side. If the user then waives a constraint (e.g. plug availability), re-search at that mark without the dropped filter.
- **Search only what the user asked, when they ask — don't pre-empt.** Run the search the current request calls for, present it, and let the user's next instruction drive the next search. Don't scout ahead into extra POI searches or chained calculations the user hasn't requested yet — e.g. hunting several charging stops and computing multiple top-ups before the user has even chosen whether, where, or with what strategy to stop. That over-acting sends the conversation down a path the user didn't ask for.

### When the found POI feeds a navigation change
- This skill finds and presents POIs. The moment a chosen POI is turned into a navigation stop or destination — added, replacing a waypoint, or set as part of a fresh single- or multi-stop route — the route-presentation duties of the navigation operation take over and still apply: detail the fastest and the shortest alternative (only one if they coincide), flag any toll roads on a route you present in detail, and **end by explicitly asking whether the user wants the remaining alternatives** before treating the matter as closed. This closing question is mandatory, not optional: proactively taking the fastest leg(s) is correct when the user didn't specify, but stating "I used the fastest route" and stopping there — without naming that you chose it and offering the other alternatives — leaves the request half-finished and fails even when every tool call was correct.
- **On a multi-stop set, this applies per route segment.** When you set a route with an intermediate stop (e.g. a charging station before the destination), you take the fastest alternative for *each* leg by default, say so, flag a toll on any leg you detail, and then ask if the user wants details on the other alternatives. Merely noting "there are other alternatives" without asking does not satisfy this. Hand the actual route edit to the relevant navigation skill, but don't drop that presentation step on the way there.

### When a capability is missing
- **Category-search parameter removed.** If `search_poi_at_location` errors because `category_poi` is gone (and any along-route variant is also absent), resolve the place id, attempt the search **once**, let it error, then state precisely that the category-search parameter is unavailable so listings can't be retrieved — and offer the fallback: if the user names a specific place or address, you can hand that to navigation. Don't retry the erroring call, don't invent listing names/hours/addresses/phone numbers, and leave navigation unchanged until asked.
- Do every doable part; admit only the impossible part, once, with a forward option — don't loop a trailing question.

## Principles
- **POI resolution and search are informational; selection and follow-up actions belong to the user.** Read navigation state, resolve locations, read preferences, compute SoC distance, and run at-location or along-route POI searches directly to present candidates. Do not auto-pick a POI, call it, add it as a waypoint, change navigation, or apply extra filters beyond the user's constraint; wait for the user to choose the POI or ask for the follow-up action.
- **Match the resolution method to how the place was given.** Named → name lookup; "my destination" → navigation state final waypoint; "my next stop" → navigation state first upcoming intermediate waypoint; along the route → route id + kilometre mark. Read the destination/stop, don't ask for it.
- **Infer the category from preference; ask only for a genuine open choice.** The preference (or a named category) settles the category silently; the POI selection is the real choice left to the user.
- **The user picks the POI.** Search surfaces the options; never auto-select one. Include phone numbers when a call may follow, so the chosen POI's own number is on hand.
- **Fulfil the doable parts, refuse only the impossible one.** Resolve, search, present — then admit any single missing piece, naming it precisely.
- **Filter to the constraint, not beyond it.** Add a filter only when the request demands it, and remove a filter the moment the user waives that constraint — an over-narrow filter set silently drops valid candidates.
- **"Open" is relative to when the user will be there.** Match `opening_hours` against the arrival/stop time, not the current clock; reserve `any::currently_open` for genuinely now.
- **Don't loop.** Refuse or admit once with a forward option, then stop; never call a removed-parameter tool repeatedly, fire dozens of near-identical searches, or fabricate a result.

## Common mistakes to avoid
- **Asking "what kind of place?"** instead of taking the category from the preference, or **inventing a category** instead of reading the preferred one.
- **Asking where the destination is** instead of reading navigation state, or **name-resolving a place that was "my destination"** (or vice versa).
- **Searching the final destination when the user said "my next stop"** on a multi-stop route — the next stop is the first upcoming intermediate waypoint, not the endpoint.
- **Using the along-route search for a named place**, or the at-location search when the user asked along the route at a kilometre mark.
- **Searching before resolving the location/route id**, or searching the wrong category.
- **Auto-selecting a POI** instead of presenting candidates and letting the user choose.
- **Dialing a found POI** — that is the `place-phone-call` skill, not this one; **setting navigation** to the POI when the user only asked to find it.
- **Fabricating listings** — inventing names, hours, addresses, or phone numbers when search can't run.
- **Over-stripping the place name** — reducing a distinctive city name to a partial term (e.g. "Andorra la Vella" → "Andorra") and then giving up on a not-found; strip only a country/qualifier suffix, retry with the full name, and only then ask for a nearby place.
- **Guessing or fabricating a location/POI id**, or firing a dependent route/search call with a guessed id in the same parallel batch as the resolution — wait for the real id the lookup returns.
- **Retrying the erroring search** hoping the removed parameter returns.
- **Refusing the whole task** when the search-and-present is fully doable, or **looping a trailing question** every turn so the conversation can't close.
- **Using `any::currently_open` for "open when I arrive"** — it filters by the current clock and returns empty (or the wrong place) for a future arrival; fetch unfiltered and check `opening_hours` against the computed arrival/stop time instead.
- **Keeping `has_available_plug` / `has_dc_plug` (or any filter) after the user waives that constraint** — the waived filter hides the very stations that now qualify.
- **Firing many redundant identical along-route searches** across tightly-spaced kilometre marks instead of a few well-placed probes, or sweeping endlessly rather than reporting honestly when nothing in the stated window matches.
- **Searching a charger at an arbitrary kilometre when a stored preference pins the point** — for an unstated "somewhere along the route" charging stop, read the charging-station preference, convert it to a route distance (an SOC target via `get_distance_by_soc`, mapped onto the right leg), and search there, rather than guessing a round number or asking the user.
- **Scouting ahead with searches/calculations the user hasn't asked for** — e.g. hunting a second or third charging stop and computing several charge times before the user has chosen a strategy. Do the requested search, present it, and let the next instruction drive the next step.
- **Turning a found POI into a route stop/destination but skipping the route-presentation duties** — when a chosen POI becomes a navigation change (including a fresh multi-stop set with an intermediate charging/food stop), you must still detail the fastest and shortest alternatives per segment, flag tolls on a detailed route, and **finish by asking whether the user wants the remaining alternatives**. Picking the fastest leg(s) and ending with "I used the fastest route" — without offering the other alternatives — is a failure even when the legs and the stop were all correct. Merely stating "there are other alternatives" without actually asking does not count.
- **Proposing a stop that satisfies only one of two required conditions** — when the user needs two categories at the same stop (charger + open food, etc.), search both around the candidate mark and choose a point where both hold, rather than offering a charger with no open food or food with no charger.

## Procedure
1. Resolve the place: "my destination" → `get_current_navigation_state(detailed_information=true)`, take the **final** waypoint's id; "my next stop" → same call, take the **first upcoming intermediate** waypoint's id; a named place → `get_location_id_by_location_name(<the place named>)`; along the route → take the route id and the user's kilometre mark.
2. Determine the category: if named, use it; if left open, `get_user_preferences` → preferred category.
3. Choose filters from the constraints: add `any::currently_open` only for *now*; for "open at arrival/during the stop", omit it and compare `opening_hours` to the computed arrival time. Add charging filters only if the user wants an available/DC plug — drop them if the user waives plug/power/AC-DC. For an along-route charger search, set `at_kilometer` from the user's mark (convert a time window via `convert_route_distance_and_time`); if no mark is given but a charging preference exists, derive the mark from it (e.g. `get_distance_by_soc` to the preferred SOC, mapped onto the right leg) instead of guessing.
4. Search: `search_poi_at_location(location_id=<resolved id>, category_poi=<the category>, filters)`, or `search_poi_along_the_route(route_id=<route>, at_kilometer=<the mark>, category_poi=<the category>, filters)`.
   - Errors (category param removed) → state it precisely, offer name/address → navigation, stop.
   - Succeeds → present options (with phone numbers if a call may follow); wait for the user to pick one.
5. Confirm what you found and anything you couldn't; do not repeat a trailing question or sweep the route indefinitely. To dial a chosen POI, see `place-phone-call`. Stop.
