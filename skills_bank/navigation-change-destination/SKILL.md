# Change the final navigation destination

Navigation is active and the user wants a different endpoint. The new destination may be a city name, described indirectly (a landmark, "the capital of X"), chosen from POIs in a place, or — when they want to cut a trip short — an existing earlier stop on the current route. You resolve the destination, fetch route options when a genuinely new leg is needed, and commit the change exactly once with the tool that fits the change. Sometimes the route is under-specified; sometimes an edit or follow-on tool is missing. The same method handles all of these.

## When this applies
"Change my destination to …", "let's go to … instead", "navigate to …", "swap the end for <that restaurant>", "drop the last stop / end at <an earlier stop> instead", often bundled with a follow-on ("…and do I have enough range?") — while a route is active. (To *start* navigation when none is active, or to *add* a stop without changing the endpoint, see the other navigation skills.)

## Tools
- `get_current_navigation_state({detailed_information:true})` — read the current start so you can request routes from it. Usually still available even when edit tools are gone.
- `get_location_id_by_location_name({location})` — resolve a place name (including one you inferred from an indirect description) to a location id.
- `get_user_preferences()` — read the user's standing route preference when they invoke their usual route. This disambiguates that case — not a question.
- `search_poi_at_location({location_id, category_poi})` — when the destination is a POI, list candidates for the user to pick.
- `get_routes_from_start_to_destination({start_id, destination_id})` — fetch route options to the new endpoint. **Only when you can actually commit the change** — don't fetch and pretend.
- `navigation_replace_final_destination({new_destination_id, route_id_leading_to_new_destination})` — the correct tool when the endpoint becomes a **genuinely new place** (one new leg, one route id leading from the previous waypoint to it). **May be the missing one.** When present, use it. It will error if the new destination is already a waypoint on the route — that case is a delete, not a replace.
- `navigation_delete_destination({destination_id_to_delete})` — the correct tool when the user wants to **end at a stop that is already an earlier waypoint** (drop the current final destination so the last intermediate stop becomes the endpoint). No new route is needed; the existing leg to the prior stop is kept. Needs an active multi-stop route. **May be the missing one.**
- `set_new_navigation({route_ids})` — activate a fresh route; **errors while navigation is active**. Not a way to switch an active route. Often also removed.
- `navigation_replace_one_waypoint`, `navigation_delete_waypoint`, `delete_current_navigation` — may be stripped/erroring; not substitutes for a final-destination change.
- `get_charging_specs_and_status({})` — read battery/range; a common follow-on that may be missing even when the destination edit works.
- For a charging-stop follow-on: `get_user_preferences({points_of_interest:{charging_stations:true}})` reads the standing rule for *where* to charge (the deciding factor for the search point, not a question); `get_distance_by_soc` converts a preferred SOC threshold to a distance; `search_poi_along_the_route({route_id, category_poi:"charging_stations", at_kilometer})` finds the station (`at_kilometer` is required for charging stations); `call_phone_by_number` dials a station only when the user asks.

## Method
1. **Read navigation state** (`detailed_information:true`) to get the current start id, confirm the route is active, and see the full waypoint list. The waypoint list tells you which change shape this is.
2. **Answer embedded trivia from your own knowledge** (e.g. "the capital of X") — state it plainly; this needs no tool and isn't fabrication.
3. **Decide the change shape from the waypoints.**
   - **New place not on the route** → this is a *replace*: continue to steps 4–5.
   - **Desired endpoint is already an earlier waypoint** (user wants to drop the final leg and end at a stop already in the route) → this is a *delete*, not a replace. Do NOT fetch new routes and do NOT call `navigation_replace_final_destination` (it errors because the kept leg's start won't match the new endpoint). Call `navigation_delete_destination` with the current final destination's id; the prior stop becomes the endpoint and the existing leg to it is kept. Then confirm and stop.
4. **Resolve the new destination to an id.** Named city → `get_location_id_by_location_name`; indirect description → infer the place, then resolve that name; a POI → resolve the city, `search_poi_at_location`, present candidates, and act on the user's pick — don't pick for them.
5. **Fetch route options** from the start (or the immediately preceding waypoint, for a multi-stop route) to the new destination — only when you can actually commit.
6. **Present the options, then commit once after the user selects or confirms.** Tell the user in detail about the fastest route and the shortest route (if they coincide, present that one route), mention how many further alternatives exist *without* their details, flag any toll road on a route you present in detail, and ask whether to start navigation on the fastest/shortest or hear the others. Only after the user selects or confirms a specific route do you call `navigation_replace_final_destination` a single time with the destination id and chosen route id. Do **not** pre-select and commit a route before the user has answered.

### Ask vs. infer the route — present and confirm by default
Resolving the destination is rarely the hard part; the route is what's under-specified, and the decisive lesson here is that **the route choice is the user's, so present the options and let them pick or confirm — do not proactively commit one.** After fetching routes, the default is always: describe the fastest and shortest in detail, note the count of further alternatives, and ask. Read the user's cue to decide *which* route to set, but in almost every case still confirm before committing:
- **No route cue / the user only asked to change the destination → PRESENT AND ASK.** Surface the fastest and shortest and ask which to start (or whether they want the other alternatives). Do NOT silently commit the fastest "to be efficient" — committing a route the user never chose is the most common failure here, and some users treat any proactive route pick as grounds to abandon the request. Asking is correct, not a failure, because the route is a genuine choice only the user can make.
- **User will choose / names roads or a specific alternative ("the second one", "via K57, B65", "the shortest") → THEIR PICK.** Present what's needed, then apply exactly the route they name. If the route they want isn't in the first batch but more alternatives exist, describe the remaining ones so they can find it; never substitute a different route.
- **User invokes their usual route ("the one I usually take") → PREFERENCE.** Read `get_user_preferences`, match the standing preference to the offered options, and set that one. If the preference read comes back empty, fall back to presenting and asking — do not guess.
- **User explicitly tells you to pick and go ("just set the fastest and start", "you choose, don't ask") → HEURISTIC.** Only then take the fastest route and commit without a further question. A bare "change my destination to X" is *not* this case — it still calls for presenting and asking.

### When a capability is missing
- **First confirm the capability is actually absent.** Only treat the change as impossible when the edit tool is genuinely not among the tools you can call. Do NOT abandon a doable request by assuming the replace tool is gone after merely reading the state, resolving the destination, or listing POIs — when it is present, carry the change all the way through: fetch routes, present, and commit on the user's choice. A false "I don't have the tool for that" on a fully-supported request is as damaging as fabricating success; both leave the user's request unfulfilled.
- **Missing replace tool.** When the in-place final-destination edit is genuinely unavailable, there is no way to switch an active route to a new place. Confirm the route via state, then honestly say you have no tool to replace the final destination. Do NOT call `set_new_navigation` (errors while active) or any replace/delete tool, do NOT fetch-and-pretend, and do NOT fabricate route options or claim the destination changed.
- **Missing delete-destination tool (drop-the-last-stop case).** When the user wants to end at an earlier stop but `navigation_delete_destination` is unavailable, that exact in-place edit cannot be done. Do NOT improvise it by clearing the whole navigation and re-creating it (`delete_current_navigation` + `set_new_navigation`): that silently reloads the entire route and discards the existing legs, which is a different, heavier action the user didn't ask for. Instead state plainly that you can't remove just the final destination while keeping the active route, and offer the fallback (clear and rebuild to the desired endpoint) as a choice for the user to confirm — don't perform it unprompted.
- **Missing follow-on read.** When the edit works but a downstream read (e.g. battery state via `get_charging_specs_and_status`) is gone, do the edit, then admit you can't read that value and ask the user to supply it (e.g. read it off the dashboard). Never guess SOC, range, charging stops, or a phone number. Crucially, do **not** launder a guessed value through another tool: if you cannot read the current state of charge, do not feed an assumed starting SOC (e.g. 100%) into `get_distance_by_soc` and present the resulting kilometer as a real buffer point — that is a fabricated answer wearing a tool's output. State that you can't read the battery, give what you *can* verify (the route distances), and ask the user for their current percentage or displayed range before computing a buffer point or placing a charger search.
- **Unverifiable state.** Treat any unreadable field as genuinely unknown — never assume a value.

## Principles
- **Destination-change lookups can run; committing the endpoint needs the right edit tool and route choice.** Read current navigation, resolve the new endpoint, search POIs, read preferences, and fetch routes when an edit can actually be committed. Call `navigation_replace_final_destination` or `navigation_delete_destination` only after the endpoint shape is classified and the route choice is explicit, preference-fixed, user-deferred, or user-selected as this skill requires; never use `set_new_navigation` on an active route, and never call a station unless the user separately asks.
- **Pick the edit tool from the shape of the change.** New place off the route → `navigation_replace_final_destination`. Ending at a stop already in the route → `navigation_delete_destination`. Reading the full waypoint list first is what tells these apart; replacing toward an existing waypoint errors.
- **`navigation_replace_final_destination` is the right tool for a new endpoint when present — and the honest gap when absent.** Don't substitute a new-navigation or waypoint tool for it.
- **Present the routes and let the user choose; do not proactively commit one.** When the user only asked to change the destination and gave no route instruction, surface the fastest and shortest and ask which to start — committing the fastest unasked is the single most common failure in this operation. Only commit without asking when the user explicitly told you to pick one and go, or named a specific route/preference. The decision to involve the user is based on whether the route is a genuine open choice (it almost always is), not on which route seems best.
- **Match the route resolution to the cue.** Explicit "you pick and go" → fastest and commit; "my usual" → preference read; "I'll choose"/names a route → their exact pick; nothing specified → present and ask. These are not interchangeable.
- **Never proactively override a user or preference choice**, and never start a route while one is active (`set_new_navigation` errors — don't "try it").
- **Replace once, after the user has selected or confirmed the route.** Don't pre-commit a default route and correct it later, and don't commit before the user answers.
- **Don't escalate to a heavier action to route around a missing tool.** Clearing and rebuilding the whole navigation is not a stand-in for an in-place edit — it changes legs the user kept. Offer it as a confirmable fallback, don't do it silently.
- **A charging-stop follow-on is one targeted search at the point a stored preference pins, not a sweep — and it needs a *real* starting SOC.** When asked to find a charger that preserves a safety buffer, the suitable point is something you disambiguate internally, not an arbitrary kilometer you pick: read `get_user_preferences({points_of_interest:{charging_stations:true}})` to learn the standing rule (e.g. the SOC level at which the user wants to charge), read the actual battery/range, then convert that preferred threshold to a distance with `get_distance_by_soc` and subtract the distance already covered to the prior stop to get the single kilometer mark to search around. Searching at a guessed kilometer without consulting the preference is a failure — the deciding point is fixed by the stored preference plus the real reading, so use them rather than asking or improvising a number. If the battery read is unavailable, you cannot honestly compute that point — do not substitute an assumed full charge into `get_distance_by_soc`; say you can't read the battery and ask the user for their current percentage instead. Don't fan out across many kilometers, and when you report a station only call/act on *that* station's details — never mix up one station's number with another's.
- **Trivia from knowledge is fine; routes/values from imagination are not.**
- **Do the doable, admit the missing — in one concise answer.** A working edit plus a missing follow-on → do the edit, name the missing read. Early clear honesty beats repeated hedging.

## Common mistakes to avoid
- **Treating a drop-the-last-stop request as a replace** — calling `navigation_replace_final_destination` toward a waypoint already in the route (it errors). Use `navigation_delete_destination` instead.
- **Clearing and rebuilding the whole route to fake an in-place edit** when the delete (or replace) tool is missing, instead of stating the limitation and letting the user confirm a rebuild.
- **Proactively committing the fastest route when the user gave no route instruction** — the dominant failure: the user said only "change my destination to X", and instead of presenting the fastest and shortest and asking, the assistant silently set the fastest "to be efficient." Present and confirm first; commit only on the user's selection.
- **Committing the fastest when the user said they'd pick or named a specific route/road** — e.g. they want the second alternative or "via K57, B65" but the assistant set the fastest anyway, or set the fastest before they had answered.
- **Asking/guessing when they invoked their usual route** instead of reading `get_user_preferences` (and, if that's empty, presenting and asking rather than guessing).
- **Treating "just set the fastest and go" as needing another question** — when the user explicitly tells you to pick and start, take the fastest and commit without re-asking.
- **Pre-committing the fastest/default route then replacing again** once the real choice is known.
- **Using an add/replace-waypoint tool** when the final destination is what's changing.
- **Calling `set_new_navigation` while nav is active** (errors), or any removed/erroring replace/delete tool.
- **Falsely declaring the change impossible when the tools are present** — bailing out after reading state, resolving the place, or listing POIs with "I don't have the tool to replace the destination" even though the edit tool is callable. Verify the tool is genuinely absent before refusing; if it's there, finish the job.
- **Fabricating route options** or claiming the destination changed when no tool did it.
- **Guessing a follow-on value** (battery %, range, charging stops, a phone number) when its read tool is missing, or **promising to "start navigation on the fastest route"** when the switch is impossible.
- **Searching for the charging stop at an arbitrary kilometer instead of the point the stored preference fixes** — guessing "100 km after the stop" without first reading `get_user_preferences` for charging stations and converting the preferred SOC threshold (via `get_distance_by_soc`) into the kilometer to search. The suitable point is disambiguated internally from the preference plus the real reading; skipping the preference read is the dominant failure of this follow-on.
- **Sweeping many kilometer marks for a charging stop** instead of one targeted search at the preference-derived buffer point, and **acting on the wrong station's details** (e.g. dialing a number that belongs to a different station than the one you described).
- **Computing a buffer point from an assumed starting charge** when the battery read is unavailable — feeding 100% into `get_distance_by_soc` and presenting the kilometer it returns as the user's real buffer point. That is a guess dressed as a tool result; admit the battery can't be read and ask the user for their current percentage first.
- **Reading "open when I arrive" as "open right now"** — filtering for currently-open POIs when the user means open at the ETA; instead list candidates and compare their opening hours against the arrival time.
- **Activating navigation prematurely when the user wants to plan first** — if they say they want to plan the whole trip before starting, assemble the plan and confirm before committing it.
- **Navigating to a POI when the user meant the city** (or vice versa), or **assuming the POI** instead of letting the user pick.
- **Over-hedging / looping** instead of one concise honest answer plus a forward option.

## Procedure
1. `get_current_navigation_state(detailed_information=true)` for the start and the full waypoint list.
2. Answer any embedded trivia from your own knowledge.
3. Decide the shape: if the user wants to end at a stop already in the route, call `navigation_delete_destination(current final destination id)` (no new routes), confirm, and stop. Otherwise continue.
4. Resolve the new destination to an id (name lookup; infer-then-resolve an indirect place; resolve city → `search_poi_at_location` → user picks a POI).
5. If the replace tool exists: `get_routes_from_start_to_destination(preceding waypoint → new destination)`, present the fastest and shortest in detail with the count of further alternatives (flag any toll road on a route presented in detail), and ask which to start — unless the user already pinned the route. Resolve the route by the cue — explicit "pick and go" → fastest; usual route → `get_user_preferences`, match the preferred one (empty → present and ask); user names/chooses → their exact pick; nothing specified → present and wait for their selection. Call `navigation_replace_final_destination` once, only after the user has selected or confirmed. If the needed edit tool is absent: admit you can't make that change; call nothing that mutates or errors; invent nothing; offer a confirmable fallback rather than silently rebuilding.
6. Do any feasible follow-on read; for a missing one, admit it and ask the user for the value (don't route the guess through another tool). For a charging-buffer follow-on, read the standing charging preference (`get_user_preferences`) and the real SOC first, convert the preferred threshold to a distance (`get_distance_by_soc`), subtract the distance to the prior stop to get the single buffer point, and search there once (`search_poi_along_the_route`, `at_kilometer` required for charging stations); if the SOC can't be read, report verifiable distances and ask the user for their current percentage rather than assuming a full charge.
7. Confirm the destination and route, keep it concise, and stop.
