# EV range / charging feasibility and the charging math (information only)

The user is gathering numbers about range or charging — "how far between these two charge levels?", "can I reach <place> on what I have?", "how long would a charge here take?", "how many charging stops would this trip need?". These are **read-only** questions: you gather numbers and answer. You never change navigation and you never start charging. This file owns the **charging computations** (the SoC-range and charge-time math) that other EV skills reference. Sometimes a needed bound is **unstated**; sometimes an input is **missing** (a tool removed, or a field reading `"unknown"`). The same method handles all of these.

## When this applies
"How far can I drive from X% down to Y%?", "what's my range between these levels?", "can I make it to <destination> without charging?", "will my current battery get me there?", "how long to charge here?", "if I always charge from <some low %>, how many stops to <place>?" — any read-only EV range / charging estimate, or the charging math another skill needs.

**Sibling boundary.** This skill is read-only: it answers range/charging questions and may *find* a charger, but it never edits navigation. Actually *modifying* the route (remove / replace / add a waypoint, change the destination, add a charging stop, start navigation) is a separate navigation operation — defer those tool calls to it. When a single turn mixes a navigation change with a charging-feasibility check (e.g. "drop this stop, and will I need to charge?"), do the feasibility part here, but the navigation change must still honor its own rules: when the edit yields a multi-stop route and the user didn't specify route selection, take the fastest per segment, **explicitly tell the user you took the fastest and offer alternatives**, and flag any toll. Silently applying a chosen route without surfacing that choice is the failure.

## Tools
- `get_distance_by_soc({initial_state_of_charge, final_state_of_charge})` — distance obtainable between two state-of-charge percentages; let it carry the arithmetic (e.g. derive a stop count from the per-charge range). May be the MISSING tool.
- `get_charging_specs_and_status({})` — read current remaining range / state of charge / battery capacity / plug specs. May be MISSING, or may return a field as `"unknown"`.
- `get_user_preferences()` — read the standing charge level the user tops up to; this fixes an otherwise-unstated target/upper state of charge.
- `get_location_id_by_location_name({location})` — resolve a destination name to an id (for the "can I reach X?" variant).
- `get_routes_from_start_to_destination({start_id, destination_id})` — read the route distance to compare against range (information only). May return the distance field as `"unknown"`.
- `search_poi_at_location({location_id, category_poi, filters})` — find a charger **at the current location** (e.g. one with an available plug) when the question is about charging *here*; generally still works and can be offered proactively.
- `search_poi_along_the_route({route_id, category_poi, at_kilometer, filters})` — find a charger **along a route segment** at a given kilometer (`at_kilometer` is required for `charging_stations`); use when the user wants a stop *on the way* or at the point where the battery will hit a buffer level. Crucially, `at_kilometer` is measured **from the start of that route segment**, not from the current car position — see the offset note in the Method.
- `calculate_charging_time_by_soc({charging_station_id, charging_station_plug_id, start_state_of_charge, target_state_of_charge})` — charge time between two SoC levels.

## Method
**Range between two charge levels.** Take the two percentages exactly as the user states them and call `get_distance_by_soc({initial_state_of_charge:<the start % the user gave>, final_state_of_charge:<the end % the user gave>})`. The starting level is `initial`, the lower/target level is `final` — don't swap them, and don't invent an end value (don't assume down-to-empty when the user named a safe buffer). Report the distance and stop.

**"Can I reach X without charging?"** Read `get_charging_specs_and_status` for the current remaining range; resolve the destination with `get_location_id_by_location_name`, then `get_routes_from_start_to_destination` for the route distance. If a route is already active and the question is about the set trip, read its distance from `get_current_navigation_state` (detailed) instead of re-resolving. **Compare** range against distance and state the conclusion clearly — possible or not, and if not, the shortfall. For a **multi-leg** trip (an active route with waypoints), sum the leg distances for the total, but also pinpoint **where** range runs out — e.g. "Frankfurt is fine, but the Barcelona leg after it is 1257 km, beyond your range, so you'll need to charge after Frankfurt." Naming the leg is far more useful than a bare total. Take no car action.

**"How long to charge here?" (the charge-time math).** Read `get_charging_specs_and_status` for current SoC and plug specs. Use `search_poi_at_location` at the **current location** (filtered to an available plug) to get the charger and its plug — for a charger wanted *here / nearby / now*, search at the location; do not silently substitute a charger found *along a route* (that is a different ask). Then `calculate_charging_time_by_soc` with `start_state_of_charge` = the **current** SoC (never zero), the relevant plug, and the target SoC. **Disambiguate the station/plug by context before asking, and when several are found read the stored preference to choose:** if only one nearby station actually has an available (or available fast/DC) plug, that station is determined by the result — compute for it rather than asking "which station?". When **more than one** station is returned, the stored charging-stations preference may itself pin the pick — read `get_user_preferences` (points_of_interest → charging_stations): a criterion there (e.g. "prefers DC over AC", a provider) selects the station/plug, so apply it silently and proceed with that one. Falling back to listing every station and asking "which one?" when the preference (or availability, or a stated criterion like "fastest") already singles one out is the failure. Only when two or more stations remain genuinely valid and **nothing** — request, preference, stated criterion, or availability — pins one do you surface the options with their times instead of committing. When the preference comes back empty and nothing else decides, lead with the one that best fits the user's stated criterion or current availability rather than bouncing the choice back. Apply any arrival-time or range buffers the user gave to derive min/max as asked. Report the time and stop.

**"Where will I hit X% — find a charger there." / "find a suitable charger." (the buffer-point search).** This is the highest-leverage place to get the arithmetic right, and the most common failure is searching an arbitrary kilometer instead of deriving the right one. If the user gives the buffer level, use it. **If the user leaves the point open ("find a suitable charging station", "I'll need to charge — find one"), the buffer level is fixed by the stored preference — read `get_user_preferences` (points_of_interest → charging_stations) and use the SoC level it names** (e.g. "charge around where 15% is left") as the `final_state_of_charge`. Do NOT pick a round number like 100 km yourself, and do NOT skip the preference: that is exactly what turns a correct search into the wrong charger. Then compute how far the car can go before that level with `get_distance_by_soc({initial_state_of_charge:<current SoC>, final_state_of_charge:<the buffer % from request or preference>})` — this distance is measured **from the current car position**. Translate it into the `at_kilometer` of the route segment you will search, because `search_poi_along_the_route` measures `at_kilometer` from the **start of that segment**, not from the car. If the buffer point falls on a later leg (e.g. the active route is Leipzig→Frankfurt→Barcelona and the point lands on the Frankfurt→Barcelona leg), subtract the distance of every earlier leg before searching: `at_kilometer = buffer_distance_from_car − sum(earlier leg distances)`. Searching the later segment at the raw from-car distance overshoots by exactly the earlier legs and finds the wrong charger or nothing. Read the active route legs (`get_current_navigation_state` detailed) to get those leg distances. Then `search_poi_along_the_route` on the correct segment at the translated kilometer.

**"How many stops?" (the stop-count math).** Get the per-charge usable range with `get_distance_by_soc` over the target → low-level span (e.g. preferred top-up % down to the stated recharge threshold), then divide the trip distance by it, rounding **up** to whole driving legs. Account for the **current SoC**: if the car is already at or below the recharge threshold, the first charge happens at departure, before any leg. Commit to **one clear figure** for exactly what the user asked — and if you mention both an en-route count and a total-including-departure, label which is which so it doesn't read as two competing answers. Report it and stop; don't drift into adding a stop or routing.

### When a bound is unstated — infer it, don't ask (the crux)
- **An unstated upper/target charge level comes from the stored PREFERENCE.** When the user gives only a start/low level (or nothing) and leaves the level to charge *to* open, read `get_user_preferences` and use that as `target_state_of_charge`. Don't ask "what should I charge to?" and don't pick a number yourself.
- **An unstated charging *point* also comes from the stored PREFERENCE.** When the user says "find a suitable charging station" without naming where or at what charge level, the preference fixes the SoC level at which they want to charge — read `get_user_preferences` (charging_stations), turn that level into a from-car distance via `get_distance_by_soc`, offset it onto the right segment, and search there. Picking an arbitrary `at_kilometer`, or asking the user where to look, is the failure — the deciding value is readable, so read it.
- **But if the preference is EMPTY and the user named no buffer, the search point is a genuine choice only the user can make — ASK, don't guess.** The buffer level (or kilometer) is not pinned by anything readable, so picking a round number like 100 km or 300 km is inventing a value. Ask which battery buffer to aim for (e.g. 10%, 15%, 20%) and search once they answer. Read the preference *first*; only fall back to asking when it comes back empty.
- **Frame the SoC bounds correctly.** Charge time runs from the **current** SoC up to the preferred target. Range-per-leg comes from `get_distance_by_soc` over the target → low-level span — not from the current remaining-range readout.
- **If your context already pins every bound, do NOT ask.** Ask only when a genuinely required choice is truly unspecified and unresolvable from the values the user gave, the preference, or current state. A value the user already named, or one the preference/state fixes, must not trigger a question.

### When an input is missing — be honest, don't fabricate
Three ways an input goes missing: the range/range-by-SoC tool is **removed** (capacity, consumption, and range all unobtainable, so an exact distance is uncomputable); a status field reads `"unknown"` (e.g. remaining range or battery capacity); or the route distance reads `"unknown"`. In every case:
1. **Read what you can** — call the status/route/location tools that still work; note any removed tool and any `"unknown"` field.
2. **Detect the gap and don't estimate.** A missing or `"unknown"` number is not a number — never derive a km range from the state-of-charge percentage, and never invent the route distance. **When `get_distance_by_soc` is the removed tool, the two-SoC distance is simply uncomputable — even if `get_charging_specs_and_status` still works and shows a `remaining_range`.** Do NOT reach for `calculate_math` to scale that readout by the SoC span (e.g. `remaining_range × 75/100` for a "75% to empty" ask): the consumption curve is not linear and that readout is for the *current* charge, so any such multiplication is a fabricated answer, not a clever workaround. The dedicated SoC tool is the only valid source for a between-levels distance; with it gone, refuse and offer the manual path. Likewise, **when the current SoC itself is unavailable, you cannot place a buffer point or judge feasibility** — do not assume a full battery (or any other level) just so `get_distance_by_soc` will return something. `get_distance_by_soc` may still be callable, but feeding it an invented `initial_state_of_charge` produces a confident-looking but fabricated answer; that is the failure, not a workaround. Say you can't read the value, recommend the safe action, and offer the manual path instead.
3. **State the gap precisely**, attributing it to the specific missing tool or `"unknown"` field.
4. **Give the safe recommendation.** For a long trip with unknown/insufficient range, default to recommending charging before departure rather than a fabricated "you'll make it."
5. **Offer the manual path** (e.g. a two-level ask is a fraction of full-charge range; invite the user to supply displayed range / capacity / consumption to compute from).
6. **Run the doable lookups proactively** — surface the real datum you do have, resolve the place, `search_poi_at_location` for nearby chargers, `calculate_charging_time_by_soc` once a charger is picked.
7. **Don't loop** the identical refusal; move forward each turn.

## Principles
- **Range, route, charger-search, and charge-time tools are informational here.** Read charging status, preferences, route distances, SoC-derived distances, charger candidates, and charging time directly to answer feasibility or planning questions. This skill does not activate navigation, add stops, reserve chargers, or call stations; if the user moves from "can I make it / how long" to an actual route, waypoint, reservation, or call, require that explicit action under the relevant skill.
- **Use the exact values the user gives, in the right slots.** No swapping `initial`/`final`, no invented end value.
- **Charge time starts from the current SoC, at the preferred plug.** Zero, or a different plug, gives the wrong time.
- **Feasibility needs both numbers.** "Can I make it?" requires reading the current range *and* the route distance, then comparing — don't answer from one alone, and don't guess. On a multi-leg trip, name the leg where range runs out, not just a total.
- **Distances from `get_distance_by_soc` are measured from the car; route `at_kilometer` is measured from the segment start.** When you search for a charger at a buffer point on a later leg, convert between the two frames by subtracting the earlier legs.
- **Minimal correct read sequence**, with the right POI tool for *where* the charger is wanted (here = at the current location). Let the SoC tools do the arithmetic; don't bolt on extra generic-math or broad-planning calls.
- **Unstated target charge → the preference**, not a question and not a guess; but a value the context already pins is never a reason to ask.
- **A missing number is not a number.** `"unknown"` means unverifiable — not 0, not full; never back it out from state of charge. Default to the safe action when range is unknown/short, and be useful past the refusal.
- **This is read-only.** Answer the question; never set navigation, add a stop, or start charging.

## Common mistakes to avoid
- **Swapping `initial` and `final`**, or **inventing the end percentage** (e.g. assuming down-to-empty) instead of using the value the user named.
- **Computing charge time from zero** instead of the current SoC, or **using a non-preferred plug**.
- **Reading range from charging status when a two-SoC distance was asked** — use the dedicated `get_distance_by_soc`; or **skipping the charging-status read** and guessing range in the feasibility variant.
- **Asking for the target charge level** (or inventing one) instead of reading the preference — and conversely, **asking when context already pins the answer**.
- **Picking an arbitrary `at_kilometer` (or just listing every charger) for a "find a suitable charger" ask** instead of reading the stored charging-stations preference, converting its SoC level into a from-car distance, and offsetting onto the right segment. The preference is what makes one point "suitable"; guessing a round number searches the wrong place.
- **Wrong POI tool**: searching along a route when the charger is wanted at the current location.
- **Fanning out to broad planning / generic-math tools** when a tight read sequence answers it.
- **Answering the wrong direction** of the comparison ("yes you'll make it" when range < distance).
- **A muddled stop count** — giving two competing numbers ("3 on the way, maybe 4 total") without saying which the user asked for, forgetting to round partial legs up, or ignoring that a car already at the recharge threshold must charge before the first leg.
- **Substituting an along-route charger for a "charge here / nearby" question** — search at the current location for that ask; reserve along-route search for a question that is explicitly about the route.
- **Feeding a from-car distance straight into `search_poi_along_the_route`'s `at_kilometer` on a later leg** — the buffer distance from `get_distance_by_soc` is measured from the car, but `at_kilometer` is measured from the start of the segment being searched. Subtract the earlier legs first; otherwise you overshoot by exactly their length and search the wrong spot.
- **Committing to one plug/station when several valid ones fit and nothing pins the choice** — surface the options instead of silently picking.
- **Fabricating a km range or feasibility verdict** from data you don't have, **deriving a range from the SoC percentage** when range is `"unknown"`, or **inventing the route distance** when it reads `"unknown"`.
- **Inventing the current SoC to feed a still-callable distance/buffer tool** — when the live charge can't be read, assuming a full (or any) battery to make `get_distance_by_soc` return a number turns an honest "I can't read your charge" into a fabricated range, buffer point, or "you'll make it." A callable tool fed a made-up input is still a made-up answer; state the gap and recommend charging instead.
- **Scaling the live `remaining_range` readout by the SoC span when `get_distance_by_soc` is gone** — e.g. answering a "75% to empty" range question with `remaining_range × 0.75` via `calculate_math`. That readout reflects the *current* charge and consumption isn't linear, so the product is fabricated. With the between-levels tool removed, refuse and offer the manual path; don't manufacture a number from the status reading.
- **Guessing a buffer kilometer when the preference is empty AND the user named no buffer** — that point is a real user choice; ask which buffer (10/15/20%) rather than inventing 100 km. (Conversely, when the preference *does* name a level, use it silently — don't ask.)
- **Asking "which charging station?" instead of disambiguating** — if the nearby search returned only one with a usable plug, the result already decides; if it returned several, read the stored charging-stations preference (its criterion — DC-over-AC, a provider — picks one) or apply the user's stated criterion / current availability, and proceed with that station. Listing them all and bouncing the choice back, when the preference or a clear criterion already singles one out, is the failure.
- **Claiming to "look up" specs / a database / the web** when none is available; a **flat refusal with no workaround**; or **looping** the identical "I can't" reply.
- **Taking a car action** — starting navigation or charging — when only an answer was asked.
- **On a mixed turn that also edits the route**, applying a freshly chosen multi-stop segment (e.g. the fastest direct leg after dropping a waypoint) **without telling the user you took the fastest and offering the alternatives**, or without flagging tolls. The charging answer being correct does not excuse skipping the route-presentation duties on the navigation half of the request.

## Procedure
1. Identify what's asked (two-SoC range, can-I-make-it, charge-time-here, or stop-count) and which bounds the user gave. If the target/upper charge level is unstated, `get_user_preferences` to fix it.
2. Call the working reads the question needs: `get_charging_specs_and_status`; for feasibility, `get_location_id_by_location_name` then `get_routes_from_start_to_destination` (or read an active route's legs from `get_current_navigation_state`); for charge-time here, `search_poi_at_location` at the current location. Note any removed tool or `"unknown"` field as you go.
3. Compute with the dedicated tools: `get_distance_by_soc` for distance/stop-count/buffer-point (measured from the car), `calculate_charging_time_by_soc` for charge time (start = current SoC, preferred plug, to target) — exact slots, no swaps, no invented bounds.
4. For a buffer-point charger search: if the user didn't name the point, `get_user_preferences` (charging_stations) to get the SoC level that defines "suitable"; compute its from-car distance with `get_distance_by_soc`, translate into the target segment's `at_kilometer` by subtracting earlier-leg distances, then `search_poi_along_the_route` on that segment at the translated kilometer.
5. If a required input is missing or `"unknown"`: do not estimate it; state the gap precisely; recommend the safe action; offer the manual path; run the doable lookups proactively.
6. Report the number(s) or the conclusion (with shortfall when relevant). Set no navigation, start no charging, don't loop. Stop.
