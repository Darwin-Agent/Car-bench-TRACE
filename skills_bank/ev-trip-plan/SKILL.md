# Plan an EV trip and its charging needs

The user wants the route and charging side of a trip worked out — how far, how long, whether/where to charge, how long the charge takes, how many stops. You resolve the destination, read the battery, get routes for the preferred selection, and find/reason about a charger. **The decisive judgement is whether the user is asking for information or for a car action.** Some requests are pure info ("plan it and email the details", "how long would I need to charge", "how many stops to get there") — gather everything, change nothing. Others explicitly call for a car action ("navigate to X with a charging stop", "replace my destination", "set it up") — then set or modify navigation as asked. The same method underlies both; only the final step differs. Under-specified requests leave genuine choices (which route, which charger) that you resolve from what the user states, asking only when truly open.

## When this applies
Route + charging questions for an EV trip: "plan my trip to <place> and email <person> the route and charging details", "find a charger near the <N>-km mark / where I reach <Y>%", "charge nearby before I leave, then continue", "how long to charge / how many charging stops to <place>", "navigate to <place> with a charging stop", "change my destination and check if I'll need to charge". The unifying feature is reasoning about **range and charging** for a trip. If the request is a plain navigation change with no charging/range angle (just "take me to X", "remove a stop"), the navigation mechanics live in `navigation-start` / the waypoint-edit skills — come here when charging or range feasibility is part of it.

## Tools
- `planning_tool({...})` — optional scaffold; a malformed dependency index returns a recoverable error, so just continue with the real lookups.
- `get_user_preferences({preference_categories})` — retrieve stored preferences. Use `points_of_interest:{charging_stations:true}` when the user defers which charger or where to charge (a stored SoC threshold or preferred provider resolves it), and `navigation_and_routing:{route_selection:true}` when the route choice is left to preference.
- `get_location_id_by_location_name({location})` — resolve a destination or a named point to an id (use the city main name only). A "not found" result is real: surface it and ask for a correction; never invent an id.
- `get_charging_specs_and_status({})` — current state of charge, range, max AC/DC power, capacity. Most of the plan depends on this. It may be removed for a task, or return a field (e.g. range, capacity) as the literal `"unknown"` — treat that as genuinely unavailable, not zero.
- `get_current_navigation_state({detailed_information})` — read whether navigation is active and the current waypoints/routes. Read this before any navigation change to know whether to use `set_new_navigation` (inactive) or a waypoint-edit tool (active), and to identify which leg a charger falls on.
- `get_routes_from_start_to_destination({start_id, destination_id})` — route alternatives (distance, time, tolls, fastest/shortest aliases). Start of the overall route must be the current car location.
- `search_poi_at_location({location_id, category_poi, filters})` — chargers (or fast_food, etc.) AT a place. Use this when the user charges before leaving / at the current location / at a specific city.
- `search_poi_along_the_route({at_kilometer, route_id, category_poi, filters})` — chargers along a route; `at_kilometer` is REQUIRED for charging_stations. Use this when the user charges on the way / at a km mark / where a certain SoC is reached.
- `calculate_charging_time_by_soc({charging_station_id, charging_station_plug_id, start_state_of_charge, target_state_of_charge})` — charge time, computed from the **current** SoC at the chosen plug.
- `calculate_charging_soc_by_time(...)` — the inverse, when the user fixes a charging duration.
- `get_distance_by_soc({initial_state_of_charge, final_state_of_charge})` — distance drivable between two SoC levels; use it to find where a buffer SoC is reached and to test whether a further stop is needed.
- `convert_route_distance_and_time({route_id, time_minutes|distance_km})` — map a time on the route to a kilometre mark (e.g. to place a stop at a target arrival time) and back.
- Navigation-change tools — `set_new_navigation` (only when navigation is inactive), and `navigation_add_one_waypoint` / `navigation_replace_one_waypoint` / `navigation_replace_final_destination` / `navigation_delete_waypoint` / `navigation_delete_destination` (only when navigation is already active). **Use these only when the user calls for a car action.**

## Method
1. **Decide info vs. action first.** Re-read the request: does the user want to *know/draft/email* something, or to *change the car's navigation*? "Plan and email", "how long / how many stops", "don't set it yet", "just include it in the mail" → gather only, set nothing. "Navigate", "set it up", "replace/add this stop" → you will make the corresponding navigation call after gathering. Hold this decision through the whole turn; gathering routes and chargers is for reading numbers and is never on its own a licence to change navigation.
2. **Resolve every destination / named point id from the tool — never from memory or a guess.** Call `get_location_id_by_location_name` and use the id it returns; do not type a plausible-looking id yourself, and do not fire `get_routes_from_start_to_destination` in the *same* parallel batch as the resolution it depends on — wait for the id first. Passing an unresolved or invented id is a real tool-error failure. If a name isn't found, say so and ask for a correction (a small or unusual place may simply not be in the system); never substitute a different id to push past it.
3. **Read the battery** with `get_charging_specs_and_status` — needed for range, charge-time, and stop-count reasoning, and to decide whether charging is even needed. Do this even when the user issues a direct "find a charger at the N-km mark" order: charging feasibility for an EV trip hinges on the current charge, so the battery read is part of the standard flow, not an optional extra. If the tool is removed or a field is `"unknown"`, see "When a capability is missing".
4. **Get routes** with `get_routes_from_start_to_destination` and select per the user's stated preference (fastest, shortest, a named via). **When the user is already on an active trip — they say "my route", "I'm on my way to X then Y", "my current navigation" — read `get_current_navigation_state(detailed_information: true)` FIRST and take the legs, distances, and route ids from it.** This applies even to a pure range check before any change: don't re-resolve the destinations with `get_location_id_by_location_name` and re-query routes from scratch when the legs are already sitting in the active navigation. Re-deriving an active trip's route instead of reading it is a repeated failure even when the recomputed numbers happen to match.
   - **Single-destination, route not pinned:** present the fastest and the shortest in detail plus the count of further alternatives and let the user choose or confirm before you execute any navigation change — don't silently auto-pick and move on.
   - **Multi-stop route, per-segment selection not pinned (or user just said "fastest"):** take the fastest alternative proactively per segment — you do NOT have to ask first. But you are not finished by just setting it: after (or as) you set it, **explicitly tell the user you used the fastest alternative on each leg, flag any toll road on a chosen segment, and ask whether they'd like details on the other route alternatives.** Omitting that "I took the fastest; want the alternatives?" disclosure is the single most common failure on multi-stop setups, even when the navigation itself was correct. This disclosure-and-offer is required whether the user said "fastest" or said nothing about selection.
5. **Find / reason about the charger — search where the user framed it, and only once.** If charging before leaving or at a place → `search_poi_at_location` at that location. If charging on the way / at a km mark / "where I reach Y%" → first compute the target kilometre, then do a single `search_poi_along_the_route` there. Apply filters to match the user's stated charger preference, and **drop the availability/DC filters when the user says availability or plug type doesn't matter** — those filters hide stations the user would accept.
   - **When the user defers WHERE to charge or WHICH station ("find a suitable charger", "you decide", "according to my preferences"), retrieve the stored preference before searching.** Call `get_user_preferences({points_of_interest:{charging_stations:true}})`: it may pin a SoC threshold ("always charge around 15% left") that fixes the search kilometre, or a preferred provider/station that picks among results. Apply it silently — don't pick an arbitrary km (100, 130, 250…) or a station the preference doesn't support, and don't re-ask the user for a point they intentionally left to you. If a preference exists, converge on the single station it implies and name it; merely listing all candidates without resolving to one is a miss.
   - **Convert a "from now" distance into the right leg's kilometre.** `get_distance_by_soc` and a range figure are measured from the **current car position**, but `search_poi_along_the_route`'s `at_kilometer` is measured from the **start of the route leg you pass it**. On a multi-leg active trip you must subtract the length of every leg already covered: if the SoC buffer is reached 394 km from now and the first leg is 336 km, search `at_kilometer = 58` on the *second* leg's route id — not 394 on it. Passing the raw "from now" distance lands the search far past where the battery actually runs down and is a real, repeated failure. Use `convert_route_distance_and_time` only to turn a target arrival *time* into a distance; the leg-offset subtraction still applies afterwards.
   - **Matching a charger to an adjacent POI and/or a time window** (e.g. "a charging stop with an open fast-food place, starting between 19:00 and 19:45"): both constraints must hold at the **same** route kilometre. Convert the time window to a km range, search **both** categories there, and accept a point only where a charger AND a qualifying open POI coincide. Respect the POI category literally — fast food is not a bakery or restaurant; a station with a bakery nearby does not satisfy "fast food." Check the POI's opening hours against the **projected arrival time** at that km, not "currently open" now. The waypoint you set is the **charging station** (not the food POI), and if the user waived plug filters, search chargers without them.
6. **Compute charging** from the **current** SoC to the target at the chosen plug with `calculate_charging_time_by_soc`. To answer "how many stops", divide the route distance by the per-leg range you get from `get_distance_by_soc` between the user's charge-to and charge-from levels.
7. **Test for a further stop; report it, don't silently plan it.** Use `get_distance_by_soc` to see whether the remaining distance after the charge exceeds the resulting range. Mention any additional stop needed.
8. **Finish according to step 1.** If info-only: assemble the route + travel time + charger details + charge time + any further-stop note and present/hand it off (emailing is `send-email` with the recipient via `contacts-lookup`). If the user called for a car action: make exactly the navigation change requested (see below), then confirm what was set.

### Making the navigation change (only when the user called for it)
- **Inactive navigation** → build the full ordered list of route ids and call `set_new_navigation` once. For a charging stop, the waypoint is the charging-station POI itself (not an adjacent fast-food / shop POI the user mentioned) — make the charger the intermediate stop. Fetch the leg current→charger and charger→destination, pick the preferred alternative per leg, and pass them in order (each route's destination must match the next route's start).
- **Don't execute the change on an unconfirmed route choice.** When the user said "according to my preferences" or didn't name a route, resolve the preference (check `get_user_preferences` route_selection), present the route you'd use, and act on it — but if two alternatives remain genuinely valid and tied, surface them and let the user pick rather than committing one. Where the user *did* state the route ("fastest per leg", "the one via B441"), just use it.
- **Active navigation** → use the edit tools (`navigation_replace_final_destination`, `navigation_replace_one_waypoint`, `navigation_add_one_waypoint`, `navigation_delete_waypoint`, `navigation_delete_destination`). Do **not** call `set_new_navigation` and do **not** edit multiple waypoints in parallel — issue edits sequentially so the waypoint order stays consistent.
- The start of the overall route is always the current car location. Honor the per-leg route preference the user stated (often fastest per segment for a multi-stop trip).
- **Whenever you proactively pick the fastest alternative for one or more segments of a multi-stop route, close the loop in your reply:** state that you took the fastest per segment, name any toll road on a chosen leg, and ask if the user wants details on the remaining alternatives. Setting the route correctly but never making this offer still counts as not meeting the request. **This applies in full to a "navigate to X with a charging stop" setup** — that route is itself multi-stop (current → charger → destination), and it is exactly the case where the assistant fixates on the charger/time-window match and forgets the "I took the fastest per leg; want the alternatives?" offer. Make the offer there too.

### Ask vs. infer
- **Infer silently** when the request or context pins the value: a route/charger preference the user already stated ("the fastest one", "a DC fast charger", "the one via B441"), a single matching route or charger, a km mark or SoC buffer the user gave, or which waypoint is meant when only one fits. Don't re-ask what was said, and read a deciding value once rather than looping.
- **"Fastest charger / fastest-charging station" is resolvable, not a question.** It means the station (or plug) with the highest charging power among those found — read the plug `power_kw` values and pick the highest; don't ask the user which station. Likewise "the first one mentioned" or a named station resolves directly from the results. An occupied plug is still a valid candidate when the user says availability doesn't matter or asks only for the fastest — note it's occupied, don't exclude it.
- **A deferred charger choice is resolvable from the stored preference, not a question.** When the user says "find a suitable charger / you choose / per my preferences" and declines to specify, that is a deliberate hand-off: retrieve `get_user_preferences` charging_stations and apply it (a SoC threshold fixes the km; a provider name picks the station). Resolve to one station and name it; do not bounce the choice back to the user.
- **Ask the user** only when a genuine choice is unresolved by everything available — e.g. two equally valid chargers/routes with no stated preference AND no stored preference, or which of several waypoints to replace when more than one fits. Don't invent a percentage, a km mark, a charger, or a route the user hasn't pinned.
- **A question about a charger's phone number is a request for the number, not a licence to dial it.** When the user asks "is there a phone number?" (e.g. to reserve a plug), give the number and offer to call — then place the call only after they explicitly say to (e.g. "call it"). Calling a phone number is an outward, hard-to-reverse action that also ends the conversation, so wait for the clear go-ahead; jumping straight to dialing on "is there a number?" is the failure. Once the user does say to call, dial without re-confirming.
- **A vague "where the battery gets low" is NOT a km mark — and not a stored preference either, until you check.** When the user gestures at a buffer ("somewhere before it runs out", "where it gets low") without a number, first look for a stored SoC threshold; if none exists, ask which buffer (e.g. 15%, 20%) rather than silently picking a round number like 100, 200, or 300 km. Once they give a percentage, compute the km from it. Quietly choosing an arbitrary buffer is the failure here.

### When a capability is missing
- **A battery reading is unavailable** (the read tool is removed, or range/SoC comes back `"unknown"`): say plainly you can't read that value, and do **not** fabricate a range, a charge time, or "you'll arrive at X%". Still do the doable parts — present the route, search and list chargers along it, give whatever charge math you can with values the user supplies — rather than dead-ending by only asking for the number. If a specific computation genuinely needs the missing value, name that limitation and offer the alternative (e.g. the user reads their SoC off the dash).
- **Do not silently substitute an assumed charge for a missing one.** A request like "find a charger where I reach 15%" needs the *current* SoC; if you can't read it, don't quietly pretend the car is at 100% and place the search on that — that produces a confidently wrong stop point. Say the current charge is unknown and ask the user for it (or place the search only on a figure they give), then compute the kilometre from that.
- **A routing or charger tool errors / returns nothing** at a point: report it honestly. Repeated empty or identical results mean the data isn't there — stop searching and say so; do not loop dozens of speculative searches across km marks.
- **The send/email tool itself is unavailable:** still do the full plan and compose the complete, ready-to-send message (route, travel time, AND every detail the user asked to include — e.g. the charging-station name and details), then say plainly you cannot send it from here and hand the user the finished text. Do **not** ask "Shall I send it?" as if you could, and do **not** strip out content the user explicitly requested. An email the user asked to "include the charging station details" in must contain those details.
- Fulfil the doable parts and refuse only the impossible part, in one answer.

## Principles
- **Trip planning can gather freely; route edits require explicit action intent.** Use preferences, charging status, navigation state, route lookup, POI search, SoC distance, conversion, and charge-time tools to build the EV plan and answer "what should we do" questions. Call `set_new_navigation` or any navigation edit tool only when the user wants the car's route changed now and the route, charger/stop, order, and route choices are settled; honor "just plan", "for the email", and "don't set it yet" literally.
- **Info vs. action is the headline call.** Gather freely; change the car only when the user asks. When the user says "just for the email / don't set it yet", honor it literally — no `set_new_navigation`, no waypoint edit.
- **Search the charger where the user framed it.** "Before I leave / nearby / at <city>" → at-location search; "on the way / at the N-km mark / where I hit Y%" → along-route search at a computed point. Searching the wrong place is why the expected station never turns up.
- **Compute the point once, search once.** Derive the target kilometre from range / `get_distance_by_soc` / `convert_route_distance_and_time`, then make one targeted search. Don't fan out or loop.
- **Charge time starts from the current SoC**, at the user's preferred plug — never from zero, never at a non-preferred plug/route.
- **Match the user's filter intent.** Apply availability/DC filters only when the user wants them; drop them when the user says they don't care, or you'll hide valid stations.
- **Resolve choices from what's stated; don't guess and don't re-ask what's pinned.**
- **Disclose proactive route picks on multi-stop trips.** Taking the fastest per segment is allowed without asking, but always report that you did and offer the other alternatives (and flag tolls). Setting the right route silently is still a miss.
- **Be honest about gaps.** Missing readings, not-found locations, and empty searches get surfaced, never papered over with invented numbers.

## Common mistakes to avoid
- **Setting navigation or editing a waypoint when the user only wanted information / an email / "not yet"** — the single biggest failure on the info-only requests.
- **Guessing or hand-typing a location/route id, or requesting routes in the same parallel batch as the lookup that resolves the id** — wait for `get_location_id_by_location_name` to return, then request routes with the real id. A fabricated id errors the call.
- **Pushing past a not-found destination by using a different id** instead of telling the user the place wasn't found and asking for a correction.
- **Skipping the battery read on a direct "find a charger" order** — read `get_charging_specs_and_status` anyway; charging feasibility depends on it.
- **Assuming a full (or any) charge when the current SoC can't be read** and placing a "where I reach Y%" search on that assumption — ask for the current charge instead.
- **Auto-picking a route and immediately executing the navigation change for a single destination** when the user hasn't pinned the route — present fastest/shortest and the alternative count, and confirm first.
- **Taking the fastest segment(s) of a multi-stop route but never telling the user you did so or offering the other alternatives** — for a multi-stop change you may pick fastest proactively, but you must still say "I took the fastest per leg, want details on the alternatives?" and flag any toll. Skipping that offer is the most frequent multi-stop failure.
- **Failing to set / edit navigation when the user clearly asked for it** — over-applying "info-only" to a request that called for a car action.
- **Searching along the route when the user wanted to charge at the current location (or vice versa)** — the expected station is never found.
- **Passing a "from now" distance straight into `at_kilometer`** without subtracting the legs already covered, so the charger search lands far past where the battery actually runs down (e.g. searching km 394 on the second leg instead of km 58).
- **Fanning out dozens of `search_poi_along_the_route` calls** across many km marks and looping on identical results instead of computing one target point and searching there.
- **Filtering by available/DC plug when the user said availability or plug type doesn't matter** — hiding the station they would have accepted. An occupied or AC-only plug is still acceptable then; flag it, don't drop it.
- **Picking an arbitrary search kilometre (or station) when the user deferred the choice** instead of retrieving `get_user_preferences` charging_stations and using the SoC threshold / provider it stores — and the related miss of just listing every candidate without converging on the one the preference implies.
- **Treating a vague "where the battery gets low" as a concrete km** and silently searching a round number, instead of resolving a stored buffer or asking which percentage to use.
- **Re-resolving destinations and re-querying routes for an active trip** (range check or charging question) instead of reading the legs and distances from `get_current_navigation_state`.
- **When the send/email tool is unavailable: asking "Shall I send it?" as if able to, or dropping details the user asked to include** — compose the complete message and state plainly you can't send it.
- **Mis-matching a paired-POI / time-window charging stop:** treating an adjacent bakery or restaurant as "fast food," checking "open now" instead of open at the projected arrival time, requiring charger and the open POI at different kilometres, or making the food POI the waypoint instead of the charging station.
- **Skipping `get_charging_specs_and_status`**, or **computing charge time from zero / at a non-preferred plug**.
- **Skipping the further-stop check**, or **actually planning** the extra stop when the user only wanted it mentioned.
- **Fabricating a range, charge time, or charger when a reading is `"unknown"` or its tool is removed** — and the opposite mistake of dead-ending by only asking for the value instead of doing the doable parts.
- **Using `set_new_navigation` on already-active navigation**, or **editing multiple waypoints in parallel** instead of sequential edits.
- **Calling a charger's phone number the moment the user asks whether a number is available** — give the number and offer to call; dial only after the explicit "call it."
- **On a "navigate with a charging stop" setup, picking fastest per leg but never offering the other route alternatives** — it is a multi-stop route, so the "I took the fastest; want the alternatives?" offer (and toll flag) is still required.

## Procedure
1. (Optional) `planning_tool`; continue past any recoverable error. Decide info-only vs. car-action from the request and hold it.
2. `get_location_id_by_location_name` for the destination / named point; if not found, surface and ask.
3. `get_charging_specs_and_status` — if removed or `"unknown"`, follow "When a capability is missing".
4. `get_current_navigation_state` (if a change to an existing trip is involved); `get_routes_from_start_to_destination` and select per the stated preference.
5. If a charger is needed: when the user deferred where/which to charge, first `get_user_preferences` charging_stations and let it fix the km/station. Search at-location or along-route per the user's framing, computing the target km once (range / `get_distance_by_soc` / `convert_route_distance_and_time`) and subtracting already-covered legs so `at_kilometer` is measured from the correct leg's start; filter to the user's preference (drop availability/type filters when they don't care); pick per preference (e.g. highest `power_kw` for "fastest charger"). For a paired-POI/time-window stop, search both categories at the same km, honor the exact POI category, and check opening hours against projected arrival.
6. `calculate_charging_time_by_soc` from the current SoC at the chosen plug; for stop-counts use `get_distance_by_soc` per leg; test for a further stop and report it.
7. Finish per step 1: info-only → assemble and present/hand off the plan (email via `send-email`, recipient via `contacts-lookup`); car-action → make exactly the requested navigation change (`set_new_navigation` if inactive, the edit tools sequentially if active) and confirm. For a multi-stop route where you picked fastest per segment, also state that you took the fastest, flag any toll, and offer the alternatives. Otherwise change nothing.
