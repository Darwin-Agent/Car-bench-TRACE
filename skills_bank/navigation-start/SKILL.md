# Start new navigation

No navigation is active and the user wants to begin one. You resolve the destination, fetch real route options from the current start, resolve which route per the user's cue, and **activate** it with `set_new_navigation` — the tool for a fresh start, which errors if a route is already running. A multi-leg trip that includes a charging stop is the same operation with more than one leg: resolve each leg's routes, then commit them all in a **single** `set_new_navigation` call, in order. The twist: the start tool may be missing, or its required route-id parameter removed, so navigation can't actually be activated.

## When this applies
"Navigate to <place>", "take me to <place>, start the fastest route", "set a route to <place> but charge first / where my buffer runs out", and **"restart / resume the route I stopped earlier"** — when **no** navigation is currently active. (If a route is already active and the endpoint changes, that is `navigation-change-destination`. Adding/removing a stop on an active route is the other navigation skills.)

## Tools
- `get_current_navigation_state({detailed_information})` — confirm nothing is active before starting. **May be the missing tool** — then you cannot read or verify whether a route is running.
- `get_location_id_by_location_name({location})` — resolve a destination / named place to an id. Use only the city's main name (e.g. "Berlin", not "Berlin City Center"). It may return no match (or an error) when the place is not in the database — treat that as the clarify trigger: surface it and ask for a nearby larger city or a more specific name, don't silently substitute and don't retry the same string.
- `get_routes_from_start_to_destination({start_id, destination_id})` — fetch route options (fastest/shortest/alternatives) for each leg, from the current start (or, for an onward leg, from the charger).
- `get_user_preferences()` — read a standing route preference when the user invokes their usual route, instead of asking.
- `set_new_navigation({route_ids})` — **activate** navigation when none is running. Pass every leg's route id in order for a multi-leg trip. **Errors while a route is already active.** **Its required route-id parameter may be removed**, so calling it can't actually activate navigation.

## Method
1. **Read state to confirm nothing is active.** If `get_current_navigation_state` shows a route running, this is not a start (point at `navigation-change-destination`). If the state tool is missing, admit you can't verify, and pivot to the lookups you can still do.
2. **Resolve the destination(s) to ids** with `get_location_id_by_location_name`. A place that doesn't resolve is a clarify, not a silent substitute.
3. **Fetch route options for each leg.** Single trip: current start → destination. Multi-leg with a charging stop: current start → charger, then charger → final destination.
4. **Resolve each leg's route by the cue** (see Ask vs. infer). For a **single destination** with no cue and no stored preference, **present the fastest and shortest (and the count of further alternatives) and ask** whether to start one or hear the others — do not auto-activate. For a **multi-stop trip** with no route selection stated, take the fastest per segment proactively, but **tell the user you picked the fastest and ask whether they want alternative-route info** — never silently commit the segments without that offer. When toll roads are on any presented or chosen route, say so.
5. **Activate with `set_new_navigation`** once the route(s) are settled — passing the chosen route, or **all** legs' route ids in order for a multi-leg trip — but only after every requested stop is known and any stop's constraints are verified (see below).
6. Confirm the destination and active route(s), then stop.

When the user is still **planning** the trip — "I want to plan a trip", "set the whole thing at once", "don't start navigation yet", or they announce more stops are coming — do not activate the first leg as soon as you have it. Gather every stop first, then commit the complete trip in one `set_new_navigation`. Activating the first destination early forces you to bolt on later stops with add/replace tools, which is the splitting this skill forbids.

### Restart / resume a previously stopped route
When the user asks to restart, resume, or get back on the route they stopped earlier, the previous route usually still sits in the navigation state with `navigation_active` false and its waypoints and `routes_to_final_destination_id` intact. Read `get_current_navigation_state(detailed_information=true)`, and if those stored route id(s) are present, **reuse them directly** in a single `set_new_navigation(route_ids=[...stored ids in order])` — do **not** re-resolve the destination by name or re-fetch fresh routes, since that risks picking a different route than the one the user was on. Confirm it's the same route (read back distance/duration/via from the state) so the user knows it's the one they expect. Only if the state holds no prior route do you fall back to a normal start: resolve the destination, fetch routes, resolve by cue. If the user states details to confirm (e.g. the distance and via roads), match them against the stored route before reactivating.

### The multi-leg charging trip — ONE call, all legs in order
When the trip is charger-leg + onward-leg, fetch both legs' routes, then issue a **single** `set_new_navigation` carrying both route ids in order (charger leg first, then the onward leg). Do **not** set navigation to the charger and then separately add the final stop, do **not** set only the first leg, and do **not** set-then-delete-then-reset — each split is a wrong action even when the end state looks similar. A charging trip **is a multi-stop trip**, so the multi-stop route policy applies in full: when no route selection is stated, take the fastest per segment, and after committing, **tell the user you took the fastest and ask whether they want alternative-route info** (flagging any segment with tolls). Reporting "I used the fastest route for both legs" without that offer is the same failure as omitting it on any other multi-stop trip — don't let the complexity of the charging math make you skip it. Picking/finding the charger itself is `poi-search`; the charge-time / state-of-charge math is `ev-range-feasibility`; a reserve phone call is `place-phone-call`, placed **last** after navigation is fully set. Reference those by name — this skill only commits the legs.

### Ask vs. infer the route
- **User names a route ("the fastest", "via B432", "the second one") → use exactly that route.** No need to ask or present.
- **User states a route-selection RULE in the conversation ("fastest without tolls if it's not more than 10 minutes longer", "shortest, not fastest") → apply that rule yourself**, comparing the alternatives against it and selecting the single route it resolves to. This is an explicit request, not an open choice — do **not** present the options and bounce the pick back to the user. Tell them which route the rule selected and why (e.g. "the toll-free one is only 7 minutes longer, so it fits your rule"). Making the user restate a rule they already gave is a failure.
- **User invokes their usual / "my preference" → read `get_user_preferences` and apply the stored route rule** (e.g. fastest-without-tolls) rather than asking. If the stored preference resolves the choice to one route, just activate it.
- **User defers ("just pick", "fastest is fine") → take the fastest yourself**, don't bounce it back as a question.
- **Single destination, no route cue AND no stored preference settles it → present the fastest and shortest and ASK** whether to start one or see the alternatives. This is a common failure: when the request is bare ("navigate to X" with no route mention) and `get_user_preferences` returns an empty route rule, the choice is a genuinely open one that is the user's to make — do **not** default to the fastest/shortest and activate it silently. Present, then act on their answer.
- **Multi-stop trip, no route selection stated → take the fastest per segment proactively, then INFORM the user you chose the fastest and ASK whether they want alternative-route info** (and flag any segment that includes tolls). This is the multi-stop policy and it differs from the single-destination case above: you do **not** present-and-ask each leg, you auto-pick the fastest per segment — but omitting the explicit "want to hear the other routes?" offer is itself a failure, even when the fastest pick is correct. A leg the user tied to their preference is resolved silently from `get_user_preferences`; a leg the user tied to a specific route uses that route.

### Verify a constrained stop before committing
When the user attaches hard conditions to a stop (a strict time window for arrival, a category that must be open *at that arrival time*, a place type they insist on), confirm the candidate actually meets every condition before you commit it — and against the **real** arrival time, **computed including the detour to reach the stop**, not the nominal on-route kilometer. A stop whose detour-inclusive arrival falls outside the stated window, whose paired requirement (e.g. an open eatery at the same point) isn't actually open at *that* arrival time, or whose place type is the wrong category (a bakery when the user insisted on fast food) does **not** qualify: treat it as a near-miss, keep searching or tell the user plainly you couldn't find a match, and ask whether to relax a constraint. Never commit a stop that only approximately fits and present it as satisfying the request — and when the user states the constraints incrementally, re-verify the whole stop against the full constraint set rather than patching one dimension at a time. (Finding the candidate POIs is `poi-search`; this skill only commits a stop once it genuinely fits.)

**Search only on the constraints the user actually stated — do not add filters they explicitly waived.** If the user says the stop only needs to satisfy condition A (e.g. an open paired place at the same point) and that they *don't care* about condition B (e.g. whether a plug is currently available, the power, AC vs DC), then searching with a filter for B can drop the very candidate that satisfies A and make you wrongly conclude no match exists. Honour what the user pinned and what they waived: search broadly enough that any genuinely qualifying candidate can surface, then check the real constraints on the results. When the paired requirement must hold at the same point, search each category at the same kilometer and require a candidate of *each* at that point before committing — a charger at one km and an open eatery at a different km is not a match.

### Condition-decided destination ("go to X if …, else Y")
When the destination itself depends on a fact you must check first — a weather condition, a time, a battery state — gather **only** the data the condition needs, evaluate the condition against the **actual** returned value, then commit to the single branch it selects. Read the condition literally: "if it is *not raining*" is satisfied by any non-rain condition (cloudy, sunny, foggy, snowy, …) — do not over-narrow it to "only sunny" or treat a borderline reading as the excluded case. Once the branch is fixed, the chosen destination is handled exactly like any other start (resolve, route, route-cue, present-and-ask or act). Don't fetch routes for the rejected branch, and don't blend the two.

**Evaluate a travel-dependent condition at the ARRIVAL time, not the current time.** The condition "is it raining *there*" (or any time-sensitive fact at a place you'll drive to) is about the moment you'll actually be there, which is often hours away — checking it at the current clock time is the most common way this branch goes wrong. So when the condition gates a place you must travel to: resolve that place, fetch the route to it first to get the estimated arrival time (ETA = current time + the route's duration), then query the condition **at the ETA's hour** at that location, and branch on *that* reading. The current-time slot the weather tool returns by default is usually the wrong slot — request the slot covering your arrival. Only evaluate at the current time if the condition is explicitly about "right now" or the place is the current location.

### Resolving a superlative POI destination ("the fastest / nearest / closest <place>")
When the destination is a superlative over candidates rather than a named place — "navigate to *the fastest charging station*", "the nearest bakery" — you must actually compare the candidates on the stated dimension and pick the genuine winner, not grab the first hit or a convenient one. "Fastest charging station" is decided by the station's charging speed (its highest-power usable plug), which means you generally need the **full candidate set** to compare — so do not pre-filter the search so aggressively that only one candidate survives and the comparison becomes impossible (e.g. filtering to a single plug type before you have compared stations hides the real fastest one). Gather the candidates, compare on the named dimension, and name the winner you picked and why. Finding and comparing the POIs is `poi-search`; this skill commits navigation only after the superlative is honestly resolved. If two candidates genuinely tie on the dimension with nothing else to separate them, that is an open choice — present both and ask.

### When a capability is missing
- **Missing state tool.** When `get_current_navigation_state` is absent you cannot verify whether a route is running. Don't claim nav is or isn't active; pivot to looking up routes to a destination the user names.
- **Missing start tool / removed route-id parameter.** When `set_new_navigation` is gone, or its required route input is removed, navigation cannot actually be started — while every other tool still works. Do the full lookup (resolve destination(s), fetch every leg's routes honouring each leg's cue), present the **exact route id(s)** and key details the start would need, and plainly admit you can't activate it. Never claim navigation started, never fabricate a route id.
- **Unresolvable place → ask.** If a named place doesn't resolve, tell the user and let them correct it; don't silently pick a similar-sounding place.
- **Reach the resolution, don't loop.** Carry the conversation to the explicit "can't start it, here are the route id(s)" close; re-supply the ids if asked, reiterate you can't activate, then stop.

## Principles
- **Navigation-start lookups can run; activation waits until the whole route is settled.** Read current navigation, resolve destinations, read route preferences, and fetch route alternatives to decide what can be started. Call `set_new_navigation` only when no route is active, every leg's route id is ordered, and the route choice is explicit, preference-fixed, user-deferred, or otherwise settled by this skill; do not activate a partial trip while planning or silently pick a single-destination route when fastest/shortest is still an open choice.
- **`set_new_navigation` is the activation tool when nothing is active** — and the honest gap when its input is missing. Don't reach for a replace/add-stop tool to start from scratch, and never call it while a route is active (it errors).
- **One call, all legs, in order — and don't activate early while still planning.** A multi-leg trip commits in a single `set_new_navigation`; never set-to-charger-then-append, single-leg-only, or set-then-delete-then-reset. When the user signals they're planning the whole trip or "not yet", gather all stops before the one commit.
- **Match the route resolution to the cue, and split single-destination from multi-stop.** Their explicit pick or stored preference when given → act silently; fastest when deferred. For a **single destination** with no cue and no preference, **present fastest+shortest and ask** — auto-activating silently is a failure. For a **multi-stop trip** with no selection, take the fastest per segment but **say so and offer alternative-route info** — skipping that offer is the failure.
- **A constrained stop must actually satisfy its constraints** (real arrival time inside the window, paired requirement genuinely met) before you commit it; a near-miss is not a match.
- **A condition-decided destination commits to exactly one branch**, chosen by the literal reading of the condition against the actual checked value — non-rain means any non-rain weather, not just sunny. And a travel-dependent condition (e.g. weather at a place you'll drive to) is evaluated at the **estimated arrival time** there, not the current time — get the route's duration first so you can ask for the right time slot.
- **A superlative destination is resolved by genuinely comparing candidates** on the named dimension over the full candidate set; don't over-filter the search so only one survives, and don't grab the first hit as if it were the winner.
- **Resolve, don't substitute.** An unresolvable named place is a clarify, never a silent swap.
- **Do the full lookup before the limitation**, and **never claim navigation started** when the start capability is incomplete. Surface the route id(s), not a flat "no".

## Common mistakes to avoid
- **Using a replace/add tool, or calling `set_new_navigation` while a route is active**, to start — the former is the wrong tool, the latter errors.
- **Splitting a multi-leg trip** — set-to-charger-then-append, single-leg-only, or set-then-delete-then-reset — instead of one `set_new_navigation` with all legs in order.
- **Activating the first leg while the user is still planning** ("plan a trip", "don't start yet", more stops coming), which forces a later add/replace and splits the trip — gather all stops, then commit once.
- **Auto-activating the fastest/shortest on a bare single-destination request with no route cue and an empty stored preference**, instead of presenting fastest+shortest and asking. A bare "navigate to X" leaves that route choice genuinely open.
- **On a multi-stop trip with no route selection, committing the fastest segments without telling the user you took the fastest and offering alternative-route info** — even when the fastest pick is itself correct, skipping that offer fails the multi-stop policy. **A charging trip is a multi-stop trip:** after a charger-stop route, reporting "I used the fastest route for both legs" but not asking whether they want the other alternatives is this same failure — the charge-time math is no excuse to drop the offer.
- **Asking which route when the user deferred or named their usual** instead of resolving it, or **picking a route that ignores the user's stated preference**.
- **Presenting the options and asking the user to pick when they already gave a selection RULE in the conversation** ("fastest without tolls if not more than 10 minutes longer") — apply the rule against the alternatives and select the one route yourself, then say which it picked and why.
- **Adding a search filter the user explicitly waived** (e.g. filtering chargers by available-plug when the user said they don't care about availability), which can hide the only candidate that satisfies the constraint they DID state, leading to a false "no match found".
- **Over-narrowing a condition** — reading "if it's not raining" as "only if sunny", or treating a borderline/non-rain reading as the excluded branch — and so taking the wrong destination branch.
- **Checking a travel-dependent condition at the current time instead of the arrival time** — querying the weather at a far destination for the present hour, then branching on a reading that won't hold when you actually arrive. Fetch the route first, compute the ETA, and query the slot covering arrival.
- **Resolving a superlative destination by the first or a convenient candidate** instead of comparing all candidates on the stated dimension, or **pre-filtering the candidate search so only one station survives**, hiding the genuinely fastest/nearest one.
- **Committing a constrained stop that only approximately fits** — detour-inclusive arrival outside the stated window, the paired requirement not actually open at that arrival, or the wrong place category (a bakery when fast food was demanded) — and presenting it as satisfying the request; or **patching one constraint at a time** instead of re-verifying the whole stop against every condition.
- **On a restart/resume request, re-resolving the destination and re-fetching routes** when the stopped route's stored route id(s) are still sitting in the navigation state — reuse the stored ids directly so the user gets back the exact route they were on, rather than risking a different route choice.
- **Silently substituting an unresolvable place** instead of asking the user.
- **Re-teaching the charger pick, charge math, or reserve call** here instead of pointing at `poi-search` / `ev-range-feasibility` / `place-phone-call`; or placing a reserve call before navigation is set.
- **Fabricating route options / a route id**, or **claiming navigation started/active** when the start tool can't actually activate it.
- **Stopping after listing routes** without the honest "I can't start it" admission, or **not supplying the route id(s)** the start would need.
- **Looping** on the same refusal instead of resolving and stopping.

## Procedure
1. `get_current_navigation_state(detailed_information=true)` to confirm nothing is active; if a route is running, hand off to `navigation-change-destination`; if the tool is missing, admit you can't verify and pivot to the lookups you can do. **If this is a restart/resume request and the state still holds the prior route's stored id(s), skip the resolve/fetch steps and go straight to step 5 with those stored ids.**
2. `get_location_id_by_location_name(<destination(s)>)`; if a place doesn't resolve, ask the user and resolve the correction.
3. `get_routes_from_start_to_destination(current start → destination)` — and, for a charging trip, also `(charger → final destination)`. (Find the charger via `poi-search`; do the charge-time/SoC math via `ev-range-feasibility`.)
4. Resolve each leg's route by the cue (their explicit pick / `get_user_preferences` for a usual route / fastest when deferred). When no cue and no stored preference pin it, present fastest+shortest (flag tolls) and ask whether to start one or hear alternatives, then act on the answer. If the user is planning the whole trip, gather every stop and verify any constrained stop before committing.
5. If `set_new_navigation` can activate: call it **once** with `route_ids=[<chosen route id>]` for a single trip, or `route_ids=[<leg-1 id>, <leg-2 id>, ...]` in order for a multi-leg trip, and confirm. If its required route input is removed (or the tool is gone): present the exact route id(s) and details, admit nav can't be started, and don't claim it started.
6. If a reserve call is required, place it via `place-phone-call` LAST, after navigation is set. Then stop.
