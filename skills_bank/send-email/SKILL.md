# Compose and send an email (only after confirmation)

The user wants an email sent — contact details to someone, an EV trip plan, a weather update for a meeting. You draft it, confirm, and send only on an explicit "yes". The recipient's address comes from a real resolved contact, never invented, and when more than one contact could be the recipient you ask which one. The body contains only what the user asked for or what has been settled with them — you do not invent the trip's decisions, charging plan, or numbers on their behalf. The one variant that adds a tool here is a meeting-weather update, where the body needs a weather read. Resolving the recipient/contacts is the `contacts-lookup` skill; this skill composes and sends.

## When this applies
"Email <person> the details", "send <contact> the trip plan", "email someone from my <meeting> the forecast for where we're meeting." The deliverable is a sent email; the recipient and any looked-up content have already been (or are being) resolved by `contacts-lookup`.

## Tools
- `send_email({email_addresses, content_message})` — send the message. Recipient address(es) come from the resolved contact's own details. The send validates each address against saved contacts: an address the user types that isn't on a contact can be rejected, and you have no tool to add or edit contacts — so don't promise to "add it" and don't fabricate. May be the **removed** tool.
- `get_user_preferences({preference_categories:{productivity_and_communication:{email:true}}})` — read the user's standing email preferences. Check this before sending: a stored preference can name a person to always copy (such as a secretary) or otherwise shape the recipient list. A standing recipient lives here, not in the request, so it only surfaces if you read it.
- `get_weather({month, day, time_hour_24hformat, location_or_poi_id})` — read the weather for a meeting's place around the meeting time, when the body is a weather update.
- `get_location_id_by_location_name({location})` — resolve a meeting's location to an id so the weather query can run.

## Method
1. **Use the resolved recipient's real address.** The recipient address is the one from the contact resolved via `contacts-lookup` — never a fabricated or guessed address.
2. **Assemble the body from what the user gathered — not from your own assumptions.** Include exactly the requested content and only content that is either a verified read or a decision the user actually made. For a meeting-weather update, take the meeting's location and time from its source, resolve the location with `get_location_id_by_location_name` if the weather query needs it, then read `get_weather` for that place around the meeting hour and fold the reading into the body. For an EV trip plan, the route choice, whether and where to charge, which station, and the charge target are the user's decisions — gather and report options, but do not silently pick a charging station, invent a charge percentage, or compute a battery-at-arrival figure the user never asked for and write it into the email as fact. If a figure the body would need (range, capacity, a charge calculation) is unavailable or comes back `"unknown"`, state that limitation in the body rather than fabricating a number.
3. **For any EV-trip email, read the battery before the body mentions charging — this read is mandatory, not optional.** Whenever the email will carry a trip's travel time and/or a charging stop, call `get_charging_specs_and_status` (battery state, remaining range) and compare it against the route distance before the body asserts — or quietly omits — anything about whether a charge is needed. This holds even when the user only says "find a charger and email the travel time" and never phrases it as "do I need to charge," and it holds across a piecemeal multi-turn conversation: if the route and charger were resolved in earlier turns but the battery was never read, read it now before composing. Reporting a charger's plug details while skipping the battery read leaves the email's central question (is this stop actually needed) unverified — that is exactly the difference between the runs that pass and the ones that don't. The strongest pattern gathers the deciding reads — recipient, route options, battery status, any charger search — together up front, then composes one complete, honest draft. If the read that would establish the need is unavailable or returns `"unknown"`, say so in the body rather than guessing.
4. **Check stored email preferences before drafting the recipient list.** Call `get_user_preferences` for the email category. If a standing preference names someone to always copy (e.g. a secretary) or otherwise extends the recipients, proactively offer to apply it — resolve that person's address through `contacts-lookup` the same way as the primary recipient. The user may not mention this standing recipient because they expect you to know it from preferences; surfacing it is your job, not theirs. This is disambiguation by learned preference: a recipient fixed by a stored preference is to be applied (after offering), not asked about from scratch.
5. **Draft, then ask to confirm.** Show the draft and ask the user to confirm sending.
6. **Send only on the explicit "yes".** Call `send_email` only after the user confirms — never pre-send a draft.
7. Confirm what you did (or what you couldn't, with the honest reason) and stop.

### Ask vs. infer the content/recipient
- **Confirm before sending.** Sending is the one step that always requires explicit user confirmation; the draft is shown first and goes out only on "yes".
- **Ask which recipient when more than one fits.** If the recipient name matches several contacts, or a "send to an attendee" request leaves multiple attendees as candidates, surface the candidates and ask which one — picking for the user is the failure. When the user has already named the specific person (full name, or "send it to Tina"), just use that one without re-asking.
- **Apply a stored-preference recipient proactively; don't wait for it.** A standing preference (read via `get_user_preferences`) may say to always copy a particular person such as a secretary. The user often won't restate this — they expect you to know it. So check the preference and offer to include that person rather than sending only to whoever was named in the request. This is the opposite of inventing a recipient: the addition is grounded in a stored preference, not a guess.
- **Read — don't ask — for a meeting's derivable pieces.** A meeting's location and time come from its entry, not from the user; resolve and read them.
- **Don't decide the trip for the user.** Route selection, charging stops, charge targets, and which station are the user's choices when the request leaves them open. Report the options you find and let the user choose; never invent these decisions and present them in the email as settled. If the user has already stated a preference (fastest route, a named station, charge to 100%), apply it.
- **Use what a read returns; don't loop it.** `get_weather` may answer with a nearby window rather than the exact meeting slot — take the closest available reading and proceed. Re-calling to chase an exact slot is the failure that ends in never sending.
- The recipient itself is resolved by `contacts-lookup`; don't re-resolve contacts here.

### When a capability is missing
- **First confirm the capability is actually missing.** Only treat send as impossible when `send_email` is genuinely absent from your callable tools or a required argument is gone from its schema. If the tool is present, then on the user's "yes" you must call it — do not preemptively announce "I can't send emails from here" when sending is in fact available. Falsely refusing an available action (and handing over ready-to-send text instead of sending) fails the task just as surely as fabricating success does.
- **No send tool.** If `send_email` (or a required argument of it) is unavailable, do all the doable work — compose the full body, fold in any weather/plan/contact content, and include the recipient's **actual** address — then state plainly you can't send emails with the tools available and hand the user the **exact ready-to-send message text** so they can send it themselves. Recognise this limitation *before* inviting a send confirmation: do not draft and then ask "Should I send it?" as if you could, because that promises an action you can't perform and strands the task if the user never answers. Instead, deliver the complete draft and the honest "I can't send" in the same turn. Never claim the email was sent or queued, never fabricate the recipient's address, and don't loop the admission.
- **Can't resolve the recipient's address.** If the lookup that yields the recipient's email is unavailable, or the address field comes back `"unknown"`, you cannot honestly send. Say plainly that you can identify the person but can't retrieve a deliverable address, fulfil whatever else is doable, and don't fabricate an address or send to a guessed one.
- **User-supplied address not on the contact.** If the user dictates an address that isn't the resolved contact's saved one, the send may be rejected, and you have no way to add it to contacts. Don't claim you'll add it and don't keep retrying the rejected address — explain the limitation once and offer to send to the address actually on file (after their confirmation) instead.
- **A value the body needs is unavailable.** When a number the body would carry (range, capacity, a charge figure) is missing or returns `"unknown"`, treat it as genuinely unknown: say so in the body or to the user rather than assuming a value or computing around a fabricated one. Don't re-read in a loop expecting it to fill in.

## Principles
- **Email-support reads can run; sending waits for an explicit final yes.** Read email preferences, resolve locations, and fetch weather when they supply recipients or verified body facts for the draft. Call `send_email` only after recipients, subject/body content, preference-added recipients, and unknown-value caveats are settled and the user confirms sending; do not silently add contacts, invent addresses, write unverified trip decisions as facts, or treat a draft request as permission to send.
- **Confirm before sending.** A message goes out only after the user's explicit "yes" — never pre-send a draft.
- **The recipient address is the resolved contact's own** — never fabricated. When several contacts fit, ask which before drafting.
- **Stored email preferences can extend the recipient list.** Read them before sending; if one names a standing recipient (e.g. a secretary), offer to include them proactively — the user expects this without restating it.
- **The body reports, it doesn't decide.** Put in only what the user requested or what is verified by a read or settled with the user. Open trip decisions (route, charging stop, charge target, station) are theirs to make — surface options, don't invent answers and write them as fact.
- **Honest about unknowns.** If a value the body needs is unavailable or `"unknown"`, say so; never fill the gap with a guessed number or a self-made decision.
- **Use a read's result; don't loop it.** One weather reading (nearest slot) is enough.
- **When the send is impossible, do the doable parts and hand over ready-to-send text** — never claim a send, and don't drop the composed content because the email can't go.
- **One clear answer, then stop.** Don't re-draft or re-refuse identically turn after turn.

## Common mistakes to avoid
- **Sending before the user's explicit confirmation**, or **pre-sending a draft**.
- **Guessing the recipient** when the name matches several contacts or several attendees qualify, instead of asking which one.
- **Sending to only the named recipient without ever checking email preferences**, so a standing instruction to copy someone (e.g. a secretary) is silently dropped. The user expects you to surface and offer that recipient from their stored preference — read `get_user_preferences` for email before finalising the recipient list.
- **Inventing the trip's content** — autonomously picking a charging station, choosing a charge percentage, or computing battery-at-arrival figures the user never decided, then writing them into the email as settled fact. Gather options and let the user choose.
- **Emailing an EV trip's travel time and charger details without ever reading the battery/range.** Even when the user only says "find a charger and email the details," and even when the route and charger were already resolved in earlier turns, read the car's battery state and remaining range and compare against the route distance before the body claims (or quietly omits) anything about needing to charge. Handling the trip piecemeal across turns and never once reading the battery is the failure; the runs that read it pass, the ones that skip it do not.
- **Writing a fabricated number** for a value that is unavailable or `"unknown"` (range, capacity, charge time) instead of stating the limitation.
- **Fabricating the recipient's email** instead of using the resolved contact's own address, or sending to a guessed address when none can be retrieved.
- **Promising to add or edit a contact's address**, or repeatedly retrying a user-dictated address the send rejected because it isn't on the contact, instead of explaining the limit once and offering the address on file.
- **Looping `get_weather`** chasing an exact slot, then abandoning the task without sending.
- **Re-resolving contacts here** instead of taking the recipient from `contacts-lookup`.
- **Claiming the email was sent or queued** when the send tool is gone or no address could be resolved; **not giving the user the ready-to-send text**; or **looping** the admission instead of delivering payload + text and stopping.
- **Inviting a send confirmation ("Should I send it?") when you actually can't send** — i.e. the send tool or a required argument is unavailable — instead of surfacing that limitation in the same turn as the draft and handing over ready-to-send text. Asking to send something you can't send is a false promise.
- **Falsely claiming you can't send when `send_email` is actually available** — refusing the action, or dumping the draft text, after the user has said "yes," instead of just calling the tool. When the send tool is present, a confirmed "yes" means call it. Verify the tool is genuinely absent before ever invoking the "I can't send" path.

## Procedure
1. Take the recipient's real address from the contact resolved via `contacts-lookup`.
2. Assemble the body: include the requested content. For a meeting-weather update, resolve the meeting location (`get_location_id_by_location_name` if needed) and read `get_weather({time_hour_24hformat:<meeting hour>, location_or_poi_id:<meeting location>, month, day})` — take what it returns; don't loop.
3. Check `get_user_preferences({preference_categories:{productivity_and_communication:{email:true}}})`; if a standing recipient (e.g. a secretary to copy) is set, resolve their address via `contacts-lookup` and offer to include them.
4. Draft the email in the requested tone; ask the user to confirm sending.
5. On the explicit "yes", `send_email({email_addresses:<resolved recipient address(es), incl. any preference recipient>, content_message:<the draft>})`.
6. If `send_email` (or a needed argument such as the address list) is unavailable → recognise it up front, deliver the full payload, admit you can't send in the same turn as the draft (don't ask "Should I send it?"), hand over the exact ready-to-send text; never claim a send. Confirm and stop.
