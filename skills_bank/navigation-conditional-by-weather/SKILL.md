# Conditional navigation by weather

The user makes the destination (and/or which route, or whether to stop somewhere) depend on a **weather condition** — for example, "go to A unless it's raining there, otherwise go to B." Getting this right hinges on evaluating the condition at the correct place **and the correct time**, then taking the branch it dictates, routing per the user's preference, and — when the route has alternatives — presenting them and getting a go-ahead before you start navigation. Both branches are real outcomes; querying the wrong time slot or assuming the local outcome flips the branch and sends you to the wrong place. Sometimes the weather tool is **missing**, so the condition cannot be evaluated at all.

**The time that matters is when the weather will actually affect the trip, which for a place you are driving to is your arrival time, not the current hour.** When the rule is "navigate to A if it's [not] raining there" and A is hours away, the condition is implicitly about the conditions *when you arrive* — the whole point of choosing the destination by weather is whether the weather will be acceptable on arrival. So even when the user does not say the words "on arrival," compute the arrival time before reading the weather: a destination several hours out can be dry now but raining by the time you get there, which flips the branch. Reading the *current* slot and branching on it is the dominant failure for this operation. Only treat the condition as present-tense ("is it raining there right now") when the rule is genuinely about this moment (e.g. the place is your current location, or the user explicitly says "right now").

## When this applies
"Navigate to <A> if it does/doesn't <weather condition> there, otherwise <B>", "charge in <A> unless it's raining, then drive to <B>", "take me to <A> unless it's raining on arrival, then <B>" — any request where a weather condition selects the destination, the route, or whether to make a stop.

## Tools
- `get_location_id_by_location_name({location})` — resolve the place the condition is about and the branch destinations.
- `get_weather({location_or_poi_id, time_hour_24hformat, month, day, ...})` — read the weather for the **relevant place and time**; set the hour to match the moment the condition is about. For a destination you are driving to, that moment is your **arrival time**, not now — set `time_hour_24hformat` to the arrival hour. Only use the current hour when the rule is genuinely present-tense about your current location. This single reading decides the branch. In some cases this is the **MISSING tool** — nothing else can determine the weather.
- `calculate_datetime({original_datetime, times_to_add})` — add the route duration to the current DATETIME to get the arrival time, so you read the weather at the right future slot. Use the duration of the route you'd actually take to that place; if you haven't fetched routes yet, fetch the route to the conditioned place first to learn the travel time, then compute arrival, then read the weather.
- `get_routes_from_start_to_destination({start_id, destination_id})` — fetch routes to the destination the selected branch produces. Also used earlier to learn travel time to the conditioned place so you can compute the arrival hour for the weather read.
- `set_new_navigation({route_ids})` — activate navigation on the chosen branch's route.
- `navigation_replace_final_destination(...)` / `search_poi_at_location(...)` — act on or find a POI inside the selected branch, once it is chosen.

## Method
1. **Resolve the candidate destinations** (and the place the condition is about) to ids.
2. **Determine the time to evaluate the condition at.** If the conditioned place is somewhere you are driving to, the relevant moment is your **arrival time** — fetch the route to that place to learn the travel duration, then add it to the current DATETIME with `calculate_datetime` to get the arrival hour. Use the current hour only when the rule is genuinely about your current location right now.
3. **Read the weather once** for that place at that time with `get_weather`, setting `time_hour_24hformat` to the arrival hour you computed (not 16:00 / "now" for a place hours away). The arrival slot can differ from the current slot and resolve the condition differently — this single reading decides the branch.
4. **Evaluate the condition literally and take the branch it selects.** If the "unless" clause holds (e.g. it *is* raining/hailing at the arrival slot), the **else/fallback** branch fires — go to the other place; do NOT act locally. If it is not met, the local branch fires. Neither branch is the default; the reading decides. Read the condition value honestly: if the weather field comes back unverifiable ("unknown") rather than a real condition, you cannot evaluate the rule — say so and put the branch choice to the user instead of guessing.
5. **Run only the selected branch's actions.** If the fallback fires, the local branch's work (e.g. searching a charging station at the local place) must NOT be performed.
6. **Pick the right destination inside the branch.** When the branch is "go to a <category> POI in <place>" and several POIs come back, two independent selection axes are in play and must be kept separate: the **destination axis** (which POI) and the **route axis** (which route to it). For a charging stop, "the fastest charging station" describes the **destination** — it means the station with the fastest charging capability, i.e. the highest-power *available* plug — not the station you can reach fastest and not the route. So search broadly enough to compare (e.g. by available plug, not pre-filtered down to a single result), then compare the available plugs across the stations found and select the highest-power one. This is a heuristic the request implies, so infer it silently; do not ask "which station?" once the user has said "fastest." If the user only said "a charging station" with no selector and the candidates are genuinely interchangeable, then surface them and ask.
7. **Fetch routes to the selected destination** (you may already have these if you fetched a route earlier to compute arrival time). Identify the route on the **axis the user named** (e.g. shortest vs fastest), keeping it distinct from how you picked the destination — choosing the fastest-charging station does not make "fastest route" the wanted axis. Use exactly the route preference stated, set that route id, and describe it back on that same axis (say "shortest route" when shortest was asked, even if it happens to coincide with the fastest). Default only when the user defers.
8. **Present the route(s) and get a go-ahead before activating.** When the tool returns multiple alternatives, this is its own decision point: tell the user in detail about the fastest and the shortest (or just the one route if they coincide), flag any toll roads on a route you present in detail, mention only the *number* of further alternatives without their details, and ask whether to start navigation (offering the fastest/shortest). Do not silently jump from route lookup to `set_new_navigation` — even when the user already named a route axis, surface the chosen route and confirm the start. Activate only after the user's go-ahead (or when they earlier gave an explicit start-now instruction).
9. **Activate once** with `set_new_navigation` (or `navigation_replace_final_destination` when editing an active endpoint) on the chosen route. Confirm the destination and route, note any toll, and stop.

### Ask vs. infer
The branch is decided by the weather reading, not by asking — read the condition input and follow it; do not bounce the branch choice back when you can evaluate it. When the user has named a selector for the POI within the branch ("the fastest charging station"), that selector pins the destination — infer it from the data and act; **do not re-ask "which one?" for something the user already specified**. Only surface a POI choice when the user gave no selector and the candidates are genuinely interchangeable. The route axis comes from what the user named; default only when they defer. Keep the destination selector and the route axis separate — they are answered by different data and one does not imply the other. And **selecting a route axis is not the same as authorising the start**: when alternatives exist, present them and get the user's go-ahead before `set_new_navigation` rather than auto-starting.

### When the weather tool is missing
- **First confirm it is actually missing.** Only hand the branch choice back if `get_weather` is genuinely not callable. If the tool is present, you must use it — evaluating the condition yourself is the whole job. Declaring "I can't check the weather" when the tool is in fact available is a fabricated capability gap: it skips the evaluation, drops both branches on the user, and fails the request even though everything needed was available. Default to attempting the read, not to assuming you can't.
- **The condition is genuinely unverifiable.** When `get_weather` is removed, no other tool can substitute — POI/route tools describe places, not conditions.
- **Admit the gap first, then hand the decision back.** In your first reply, say plainly you have no weather-check tool and therefore can't verify the condition; present the explicit either/or (branch A vs branch B) and ask the user to pick.
- **No premature action.** Make no tool calls to prepare a branch you have no basis to choose: don't resolve locations, fetch routes, or search POIs on assumption, and don't begin executing either branch as if its condition held.
- **Resolve, then stop.** Once the user picks a branch, execute it normally. Don't loop the refusal.

## Principles
- **Conditional-navigation reads decide the branch before any route change.** Resolve locations, fetch routes for travel time, compute arrival, read weather at the relevant place/time, and search POIs inside the selected branch as needed. Call `set_new_navigation` or a destination-edit tool only for the single branch selected by the user's literal condition, after the route or POI target is resolved; do not run both branches, start a fallback early, or turn a weather check into navigation unless the user asked for conditional routing.
- **Right place, right time — then branch.** Evaluate the condition at the time the user's rule actually refers to. For a destination you're driving to, that is your **arrival time** — compute it (route duration added to now) and read the weather at that future slot, even when the user didn't say "on arrival." A place can be dry now and raining when you get there; reading the current hour for a place hours away is the single biggest cause of taking the wrong branch here. Follow the fallback wherever the arrival-slot reading leads.
- **Apply the rule literally.** Map the actual reading to the user's if/else exactly; don't shortcut to "probably fine" and act locally.
- **Run only the branch that fired.** Skip the non-selected branch's search/stop entirely.
- **Separate the destination selector from the route axis.** "The fastest charging station" picks the *station* (highest-power available plug), not the route; the route axis is whatever the user named for the route. Resolve each from its own evidence and don't let one bleed into the other.
- **Search wide enough to choose.** When the request needs you to compare POIs (e.g. find the fastest charger), don't over-filter the search to a single result — gather the candidates so the comparison is real, then select.
- **Honour the route axis stated** (shortest vs fastest); set that route and describe it back on that axis even when fastest and shortest are the same id; convenient default only on deferral.
- **Present alternatives, then start on the user's word.** When the route has more than one alternative, lay out the fastest and shortest (with toll flags and the count of others) and ask before activating — naming a route axis tells you *which* route, not that you may start it unprompted. Even when fastest and shortest coincide, present that route and confirm rather than auto-starting.
- **Don't guess the condition.** When you can't read the weather, never assert or assume it to justify a branch — put the choice to the user.
- **Activate after the branch resolves and the user gives the go-ahead**, once; don't pre-commit and correct.

## Common mistakes to avoid
- **Checking weather at the current time for a destination hours away.** This is the most damaging mistake for this operation: the rule "go to A if it's [not] raining there" is about A when you arrive, so reading the current slot (e.g. 16:00) and branching on "it's dry now" takes the wrong branch when A is rainy by arrival (e.g. 19:00). Always compute the arrival hour and read the weather there, even when the words "on arrival" don't appear. Reading "now" is correct only when the conditioned place is your current location at this moment.
- **Skipping the arrival-time computation.** Not fetching the route duration / not adding it to now before the weather read, so you have no arrival hour to query — leading straight back to reading "now."
- **Taking the wrong branch** because the weather was read at the wrong slot, or acting locally when the condition required the fallback.
- **Searching/stopping for the local branch** when that branch did not fire.
- **Ignoring the stated route axis** (setting or announcing the fastest route when shortest was asked) — a frequent failure when the request also said "fastest charging station": that "fastest" qualifies the *station*, not the route, so the route must still follow the user's separately stated axis.
- **Confusing the destination selector with the route axis** — treating "fastest charging station" as "fastest route," or vice versa. They are two distinct decisions resolved from different data.
- **Re-asking "which station?"** after the user already named the selector (e.g. "the fastest charging station") — pick it from the plug data and proceed instead of bouncing the choice back.
- **Over-filtering the POI search** down to a single result when you still need to compare stations to identify the fastest — you can't pick the highest-power option if the search hid the alternatives.
- **Auto-starting navigation after fetching routes** — calling `set_new_navigation` straight after the route lookup without presenting the alternatives and getting a go-ahead. This is the most common failure: when several routes exist you must surface the fastest/shortest (with toll info and the count of others) and ask whether to start, even if the user already named a route axis and even when fastest and shortest are the same route.
- **Activating before the branch is correctly resolved**, then having to correct it.
- **Skipping the toll warning** on a route you present in detail or start.
- **Re-reading the weather in a loop** instead of evaluating the single reading and acting.
- **Claiming you can't check the weather when the tool is actually available** — bouncing the branch choice back to the user with "I have no weather tool" without ever attempting `get_weather`, when it is in fact callable. Confirm the tool is genuinely absent before refusing; if it's present, read it and evaluate the branch yourself.
- **Inventing the weather** ("it's not raining, so I'll route you to A") when no weather tool exists, or **calling POI/route tools to prepare a branch on assumption**, or **pretending you checked**.
- **Looping** the same "I can't check weather" line instead of offering the choice and stopping.

## Procedure
1. If the request is weather-gated and `get_weather` is unavailable: make no tool calls; reply that you have no weather tool so the condition can't be verified; offer the explicit branch choice (A vs B) and ask the user to pick; on their pick, execute that branch normally.
2. Otherwise: `get_location_id_by_location_name` for the condition's place and the branch destinations.
3. Compute the time to evaluate at. For a place you're driving to: `get_routes_from_start_to_destination(start → conditioned place)` to learn the duration, then `calculate_datetime(now, +duration)` for the arrival hour. (Current hour only if the rule is about your current location now.)
4. `get_weather(<that place>, <arrival hour from step 3>)` — once. If the condition field returns "unknown," stop and put the branch choice to the user.
5. Evaluate the condition: "unless" clause holds → fallback branch; otherwise → local branch. (No local-branch search/stop when the fallback fires.)
6. If the branch is "go to a <category> POI," search broadly enough to compare, then pick the POI the user's selector names (e.g. "fastest charging station" → highest-power available plug). Infer this silently; ask only if no selector was given and candidates are interchangeable.
7. `get_routes_from_start_to_destination(start → selected destination)` (reuse the routes from step 3 if it's the same destination); identify the route on the **named route axis**, kept separate from how the destination was picked (default only on deferral).
8. If alternatives exist, present the fastest and shortest (toll flags, count of others) and ask whether to start; activate only on the user's go-ahead (or a prior explicit start-now instruction).
9. `set_new_navigation(route_ids=[<chosen route>])` (or replace the endpoint if active).
10. Confirm the destination and route, note any toll, and stop.
